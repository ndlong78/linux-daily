Context switch rate: tách scheduler churn khỏi CPU utilization bình thường

Đọc context-switch rate cùng run queue và CPU usage để nhận diện scheduler churn, rồi drill down voluntary/involuntary switch theo task thay vì tối ưu mù.

TRỤC · MONITORINGĐỘ KHÓ · TRUNG CẤP~12 PHÚT
Runtime tested: —Documentation verified: Ubuntu/Xubuntu 26.04 LTS · Debian 13 stable · Fedora 44 · FreeBSD 15.1-RELEASELast verified: 2026-09-20

Mục tiêu

Đọc context-switch rate theo thời gian, đối chiếu run queue và CPU user/system/idle, rồi xác định khi nào cần drill down theo process/thread thay vì coi mọi mức cs cao là lỗi.

Yêu cầu tiên quyết

  • User thường đủ quyền cho các lệnh read-only trong bài.
  • Đã quen với vmstat, run queue và process time-series từ #019, #026, #040 và #061.
  • Trên Linux, pidstat thuộc bộ sysstat; nếu máy chưa có, vẫn có thể hoàn thành phần system-level bằng vmstat và không cài package giữa incident chỉ để lấy thêm một metric.
  • FreeBSD dùng vmstat riêng của BSD; không gán option/output của procps-ng Linux cho FreeBSD.

01 Bối cảnh thực tế

Một server có thể tạo rất nhiều context switch khi hàng trăm worker liên tục ngủ/chờ I/O rồi thức dậy, trong khi CPU tổng vẫn còn rảnh. Ngược lại, một workload tính toán dài có thể dùng CPU rất cao nhưng không tạo context switch bất thường. Vì vậy “context switch cao” chỉ là tín hiệu để mở rộng điều tra, không phải kết luận.

Trên Linux, vmstat báo cs là số context switch mỗi giây; pidstat -w giúp tách voluntary và involuntary switch theo task. Trên FreeBSD, vmstat cũng có trường cs cho CPU context switches nhưng cách trình bày và option khác Linux.

02 Kiến thức cốt lõi

  • Context switch: CPU chuyển execution context từ thread/task này sang thread/task khác; bản thân việc switch là bình thường.
  • Voluntary switch: trên Linux pidstat, task tự nhường CPU vì đang chờ resource chưa sẵn sàng, ví dụ I/O hoặc synchronization.
  • Involuntary switch: task bị scheduler lấy CPU, ví dụ hết time slice hoặc có task ưu tiên phù hợp hơn cần chạy.
  • Run queue: nếu runnable work tăng cùng cs và system CPU tăng, giả thuyết scheduler churn/contention đáng điều tra hơn.
  • Không có threshold tuyệt đối: đánh giá theo baseline của chính workload, số CPU, concurrency và thay đổi theo thời gian; không dùng một ngưỡng cs/s chung cho mọi host.

03 Các bước thực hiện

  1. 1. Lấy mẫu system-level trên Linux

    Ubuntu/Xubuntu · Debian · Fedora — giống hệt nhau

    Run as: user

    vmstat 1 6

    Tập trung vào r, cs, us, sy và id. Với mẫu đầu, thận trọng vì công cụ có thể phản ánh thống kê từ lúc boot; ưu tiên các dòng interval tiếp theo để so tốc độ hiện tại.

  2. 2. Đối chiếu context-switch rate với runnable pressure

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    vmstat 2 10

    Nếu cs tăng cùng r và sy, giữ giả thuyết scheduler/kernel overhead để drill down. Nếu cs tăng nhưng r thấp và CPU còn idle, ưu tiên kiểm workload nhiều wake/sleep, timer hoặc I/O thay vì kết luận CPU thiếu.

  3. 3. Trên Linux, tìm task có switching nổi bật

    Ubuntu/Xubuntu · Debian · Fedora — cần pidstat từ sysstat

    Run as: user

    command -v pidstat
pidstat -w -p ALL 1 5

    cswch/s là voluntary context switches/giây; nvcswch/s là involuntary context switches/giây. Một task có voluntary switch cao thường đang block/chờ resource; involuntary switch cao cần được đối chiếu CPU contention, priority và runnable load.

  4. 4. Trên FreeBSD, lấy cùng lớp evidence bằng vmstat BSD

    FreeBSD — KHÁC Linux

    Run as: user

    vmstat -w 1 -c 6

    FreeBSD vmstat hiển thị cs trong nhóm CPU context switches và CPU us/sy/id. Theo manual, dòng đầu là thống kê từ lúc reboot; các dòng sau mới là interval từ lần hiển thị trước.

  5. 5. Ghi timestamp và giữ cùng cửa sổ quan sát

    Ubuntu/Xubuntu · Debian · Fedora · FreeBSD

    Run as: user

    date -u '+%Y-%m-%dT%H:%M:%SZ'

    Khi so với latency, I/O, request rate hoặc monitoring dashboard, dùng cùng khoảng thời gian. Không ghép một spike cs lúc này với CPU snapshot ở thời điểm khác.

04 Kiểm chứng

Chụp nhiều interval và viết kết luận dựa trên tổ hợp tín hiệu thay vì một metric riêng lẻ.

Expected Output / Kết quả mong đợi

Linux vmstat: đọc r + cs + us/sy/id theo nhiều interval.
Linux pidstat -w: xác định task nổi bật ở cswch/s hoặc nvcswch/s.
FreeBSD vmstat: bỏ dòng since-boot, đọc các interval cs + us/sy/id.
Kết luận: nêu baseline, cửa sổ thời gian và tín hiệu nào cùng tăng.

Không có một giá trị cs/s “chuẩn” áp cho mọi host. Điều cần kiểm chứng là sự thay đổi so với baseline và mối tương quan với workload/CPU/run queue.

05 Lưu ý & Khắc phục lỗi

  • cs cao nhưng máy không chậm: có thể đó là đặc tính bình thường của workload event-driven hoặc nhiều worker; lưu baseline trước khi tối ưu.
  • pidstat không có: đừng cài package mù trong incident. Ghi system-level evidence bằng vmstat, rồi bổ sung sysstat qua quy trình package chuẩn nếu thật sự cần.
  • cswch/s cao: không đồng nghĩa scheduler ép task rời CPU; đây là voluntary switching, thường gợi ý task đang block/chờ.
  • nvcswch/s cao: cần đối chiếu run queue, CPU pressure và priority trước khi thay scheduler/tuning.
  • FreeBSD: không dùng pidstat Linux hoặc option procps-ng cho BSD; bài này giữ drill-down FreeBSD ở system-level để không gán semantics Linux sang hệ khác.

06 Bảo mật & vận hành

  • Các lệnh trong bài là read-only; ưu tiên thu evidence trước mọi thay đổi affinity, priority, scheduler policy hoặc thread count.
  • Process list có thể lộ tên service, tenant hoặc command metadata; chỉ đưa phần cần thiết vào ticket/chat và che thông tin nhạy cảm.
  • Không hạ concurrency production chỉ vì một spike ngắn; trước hết phải chứng minh spike lặp lại và liên hệ với latency/throughput.
  • Nếu cần thay process priority, CPU affinity hoặc application worker count, tách thành change riêng có rollback và đo trước/sau.

07 Bài tập tự luyện

  1. Trên Linux lab, lấy 10 mẫu vmstat khi idle và 10 mẫu khi chạy workload hợp lệ. So sánh r, cs, us, sy, id.
  2. Dùng pidstat -w chọn một task có voluntary switch nổi bật và giải thích vì sao không nên gọi đó là preemption chỉ từ metric này.
  3. Trên FreeBSD, lấy vmstat -w 1 -c 6, bỏ mẫu đầu và ghi baseline cs của 5 interval còn lại.
