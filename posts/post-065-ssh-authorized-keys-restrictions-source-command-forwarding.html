Bảo mật · SSH key policy

SSH authorized_keys restrictions: giới hạn nguồn, command và forwarding theo từng key

Một public key không nhất thiết phải có toàn bộ quyền SSH của tài khoản; gắn policy ngay trên từng dòng authorized_keys để giảm blast radius khi credential bị lộ.

TRỤC · BẢO MẬTĐỘ KHÓ · NÂNG CAO~14 PHÚT
Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASELast verified: 2026-09-03

Mục tiêu

Giới hạn một SSH key theo nguồn kết nối, command được phép và forwarding, rồi kiểm chứng policy mà vẫn giữ đường quản trị dự phòng.

Yêu cầu tiên quyết

  • Có quyền đăng nhập vào một tài khoản thử nghiệm bằng public key; không thực hành trực tiếp trên key duy nhất đang giữ phiên quản trị production.
  • Giữ một phiên SSH thứ hai đang mở để rollback nếu key thử nghiệm bị cấu hình sai.
  • Ubuntu và Xubuntu dùng OpenSSH theo cơ chế Linux/systemd; Debian và Fedora cũng dùng cú pháp authorized_keys tương tự. FreeBSD dùng OpenSSH nhưng quản lý service bằng rc.d, không dùng systemctl.
  • Chuẩn bị một public key thử nghiệm; không chia sẻ private key.

01 Bối cảnh thực tế

Một tài khoản service có thể cần SSH để chạy backup, đồng bộ file hoặc một lệnh vận hành duy nhất. Nếu thêm public key trần vào ~/.ssh/authorized_keys, key đó thường có thể yêu cầu shell, PTY hoặc forwarding tùy policy toàn cục của server.

OpenSSH cho phép đặt option ngay trước public key. from= giới hạn nguồn, command= ép một command cố định, còn restrict tắt port forwarding, agent forwarding, X11 forwarding, PTY và user rc theo một shorthand an toàn hơn.

02 Kiến thức cốt lõi

  • Policy gắn với key. Hai key của cùng một user có thể có quyền khác nhau.
  • from= không thay firewall. Đây là điều kiện bổ sung cho authentication; CIDR phù hợp khi nguồn có dải IP ổn định.
  • command= không tự tắt forwarding. Nếu cần key chỉ chạy một tác vụ, ghép với restrict thay vì chỉ ép command.
  • restrict là deny-by-default cho các khả năng phụ. Có thể mở lại từng capability như pty hoặc port-forwarding khi thật sự cần.

03 Các bước thực hiện

  1. 1. Kiểm tra file và quyền hiện tại

    Mọi hệ

    Run as: user

    ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
cp ~/.ssh/authorized_keys ~/.ssh/authorized_keys.bak-20260903

    Backup trước khi sửa. Không đóng phiên SSH dự phòng cho tới khi key mới đã được kiểm chứng.

  2. 2. Lấy IP nguồn của phiên quản trị

    Mọi hệ

    Run as: user

    printf '%s\n' "$SSH_CONNECTION"

    Trường đầu tiên là IP client hiện tại. Dùng địa chỉ hoặc CIDR đã được quản trị xác nhận cho <source-cidr>; không khóa vào IP tạm thời nếu mạng thay đổi thường xuyên.

  3. 3. Thêm một key thử nghiệm với policy hẹp

    Mọi hệ

    Run as: user

    from="<source-cidr>",restrict,command="/usr/bin/id" ssh-ed25519 <base64-public-key> linux-daily-test

    Thêm nguyên dòng này vào ~/.ssh/authorized_keys. <source-cidr> là IP/CIDR nguồn đã xác minh; <base64-public-key> là phần public key, không phải private key.

  4. 4. Giữ permission chặt cho SSH directory

    Mọi hệ

    Run as: user

    chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

    Không đổi owner sang root nếu đây là authorized_keys của user thường.

  5. 5. Kiểm tra service theo hệ điều hành trước khi test từ client khác

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: sudo

    sudo sshd -t
sudo systemctl status ssh --no-pager 2>/dev/null || sudo systemctl status sshd --no-pager

    FreeBSD — KHÁC Linux

    Run as: root

    sshd -t
service sshd status

    sshd -t kiểm cấu hình daemon; option trong authorized_keys được đánh giá khi key dùng để authentication, nên vẫn cần test đăng nhập thực tế ở bước sau.

  6. 6. Test key từ đúng nguồn

    Client có private key thử nghiệm

    Run as: user

    ssh -i <test-private-key> <user>@<server-ip>

    Kết quả mong đợi là server chạy /usr/bin/id rồi kết thúc session; không mở interactive shell.

04 Kiểm chứng

Kiểm cả positive test và negative test. Từ nguồn được phép, key phải chạy đúng forced command. Thử yêu cầu PTY hoặc forwarding bằng chính key test; request phải bị từ chối hoặc không tạo capability đó vì restrict.

Client

Run as: user

ssh -i <test-private-key> -t <user>@<server-ip>
ssh -i <test-private-key> -L 18080:127.0.0.1:80 <user>@<server-ip>

Expected Output / Kết quả mong đợi

  • Lần đăng nhập bình thường chỉ in kết quả của id rồi thoát.
  • PTY không được cấp cho key bị restrict.
  • Port forwarding không được thiết lập cho key bị restrict.
  • Key từ nguồn không khớp from= không được chấp nhận; một phương thức authentication khác có thể vẫn hoạt động nếu server cho phép.

Gỡ / Hoàn tác

Nếu policy sai hoặc cần quay lại ngay, khôi phục file backup từ phiên SSH dự phòng rồi kiểm permission.

Mọi hệ

Run as: user

cp ~/.ssh/authorized_keys.bak-20260903 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Chỉ xóa backup sau khi đã xác nhận một key quản trị hợp lệ vẫn đăng nhập được.

05 Lưu ý & Khắc phục lỗi

  • Key đúng nhưng bị từ chối: kiểm from=, NAT/VPN và IP thực tế trong SSH_CONNECTION.
  • Forced command chạy nhưng forwarding vẫn cần: không bỏ toàn bộ restrict; mở đúng capability cần thiết bằng option cụ thể sau khi review.
  • Không đăng nhập được sau khi sửa: dùng phiên dự phòng khôi phục backup; kiểm owner/mode của ~/.ssh và authorized_keys.
  • FreeBSD: không dùng systemctl; kiểm daemon bằng service sshd status.

06 Bảo mật & vận hành

Ưu tiên một key riêng cho từng automation thay vì dùng chung key quản trị. Gắn comment có owner/purpose, giới hạn nguồn bằng CIDR khi topology ổn định, và thu hồi key khi job hoặc người sở hữu không còn cần quyền.

command= chỉ ép command server-side; nếu script được gọi có quyền quá rộng, key vẫn có thể tạo tác động tương ứng. Review chính script, quyền file và dữ liệu đầu vào như một phần của trust boundary.

07 Bài tập tự luyện

  1. Tạo một key test chỉ chạy /usr/bin/id và chứng minh interactive shell không mở.
  2. Thêm from= cho subnet quản trị trong lab rồi thử từ một nguồn ngoài subnet.
  3. So sánh rủi ro giữa key trần, command= đơn lẻ và restrict,command=.

Nguồn kỹ thuật
