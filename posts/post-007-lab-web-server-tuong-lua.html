Ôn tập · Lab end-to-end

Từ máy mới đến web server an toàn, chỉ mở đúng cổng

Sáu bài đầu là sáu mảnh rời. Bài này ghép chúng thành một quy trình thật: nhận một máy mới tinh, gán IP tĩnh, gia cố SSH, dựng nginx, rồi khoá tất cả trừ đúng ba cổng cần thiết. Mảng kỹ thuật mới của lab là tường lửa — và đây cũng là chỗ bốn hệ điều hành rẽ nhánh rõ nhất: UFW, firewalld hay pf.

TRỤC · ÔN TẬP ĐỘ KHÓ · TRUNG CẤP ~12 PHÚT

01 Bối cảnh thực tế

"Dựng cho tôi một web server" là yêu cầu nghe đơn giản nhưng dễ làm ẩu: cài xong nginx, thấy trang "Welcome" là tưởng xong — trong khi SSH vẫn cho đăng nhập mật khẩu, tường lửa mở toang, và không có bản sao lưu nào. Lab này đi trọn quy trình một quản trị viên cẩn thận thực sự làm, ghép lại những mảnh đã học thành một chuỗi có thể lặp lại. Trọng tâm mới: chỉ phơi ra mạng đúng những cổng cần thiết — nguyên tắc tối thiểu hoá bề mặt tấn công.

02 Kiến thức cốt lõi

Quy trình gồm sáu bước; bốn bước đầu đã có bài riêng, ở đây chỉ nhắc mắt xích. Mảng mới là tường lửa máy chủ (host firewall) — và mỗi họ HĐH có một công cụ mặc định khác nhau:

  • Ubuntu/Xubuntu · Debian: ufw — lớp vỏ đơn giản đứng trước nftables. Trên Debian tối giản cần cài (apt install ufw).
  • Fedora: firewalld, thao tác qua firewall-cmd, tổ chức theo zone và service.
  • FreeBSD: pf — luật khai trong /etc/pf.conf, bật qua rc.conf. Không có UFW/firewalld.
  • Nguyên tắc chung: mặc định chặn vào, chỉ mở đúng cổng dịch vụ (22/80/443), và luôn cho phép SSH trước khi bật tường lửa kẻo tự khoá mình ra ngoài.

03 Mở đúng cổng trên từng hệ điều hành

Giả định các bước 1–3 đã xong (IP tĩnh, SSH gia cố, nginx đã cài). Giờ mở đúng ba cổng: 22 (SSH), 80 và 443 (web), chặn phần còn lại.

Ubuntu / Xubuntu · Debian — ufw 
# Debian tối giản: cài trước — sudo apt install ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH          # MỞ SSH TRƯỚC khi enable!
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
Fedora — firewalld 
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
sudo firewall-cmd --list-services   # xác nhận: ssh http https
FreeBSD — pf (tách riêng) 
# /etc/pf.conf
ext_if = "em0"                  # đổi theo interface thật (ifconfig)
set skip on lo
block in all
pass out all keep state
pass in on $ext_if proto tcp to port { 22 80 443 } keep state

# Bật pf: thêm vào /etc/rc.conf rồi nạp luật
sysrc pf_enable="YES"
service pf start
pfctl -f /etc/pf.conf            # nạp/kiểm tra lại luật

04 Kiểm chứng

Ba câu hỏi: nginx có đang nghe không, tường lửa mở đúng cổng chưa, và trang có trả về không?

Linux (Ubuntu / Debian / Fedora) 
ss -tlnp | grep -E ':(22|80|443)'   # cổng đang nghe
sudo ufw status verbose             # Ubuntu/Debian
sudo firewall-cmd --list-all        # Fedora
curl -I http://localhost            # kỳ vọng: HTTP/1.1 200
FreeBSD 
sockstat -4 -l | grep -E '(:22|:80|:443)'   # cổng đang nghe
pfctl -s rules                              # luật pf đang áp
fetch -qo - http://localhost | head         # fetch thay curl nếu chưa cài curl

05 Cạm bẫy thường gặp

  • Tự khoá mình ra ngoài: bật tường lửa mà chưa mở SSH là mất kết nối tức thì trên máy từ xa. Luôn thêm luật cho cổng 22 trước khi enable/nạp luật. Với máy production ở xa, cân nhắc lịch tự tắt tường lửa để có đường cứu.
  • Fedora quên --permanent: luật không kèm --permanent sẽ bay sau khi reload/reboot. Đặt --permanent rồi --reload, hoặc --runtime-to-permanent.
  • FreeBSD sai tên interface: ext_if phải khớp tên thật (em0, vtnet0, igb0…). Chạy ifconfig xem trước; sai tên thì luật không áp đúng và pf có thể chặn nhầm.
  • Nhầm công cụ: gõ ufw trên Fedora hay firewall-cmd trên FreeBSD đều "command not found". Tường lửa là chỗ khác biệt HĐH lớn nhất trong lab này.
FreeBSD ≠ Linux Không có ufw hay firewalld trên FreeBSD. Mô hình là pf: luật văn bản trong /etc/pf.conf, bật bằng pf_enable="YES" trong rc.conf, nạp bằng pfctl -f. Cú pháp luật cũng khác hẳn dạng "allow" từng dòng của UFW.

06 Lưu ý bảo mật & vận hành

  • Tối thiểu hoá bề mặt: chỉ mở cổng thực sự dùng. Nếu web chỉ chạy HTTPS, cân nhắc bỏ luôn cổng 80 (hoặc chỉ dùng để chuyển hướng sang 443).
  • Ghép với các bài trước để có lớp phòng thủ đủ dày: SSH key-only (bài #002) + tường lửa chặn mặc định + cặp DNS khai đủ hai địa chỉ (bài #001).
  • Sau khi mọi thứ chạy, sao lưu cấu hình (bài #004): /etc/nginx, quy tắc tường lửa, rc.conf/netplan… vào một repo restic — để dựng lại máy khác trong vài phút.
  • Kiểm tra lại từ bên ngoài máy (một host khác) chứ không chỉ localhost: cổng bị chặn nhìn từ ngoài mới là bằng chứng tường lửa hoạt động.

07 Bài tập tự luyện

Đi trọn quy trình sáu bước trên hai máy mới: một Debian và một FreeBSD. Kết quả cuối: cả hai đều có IP tĩnh, SSH chỉ nhận khoá, nginx trả trang qua cổng 80/443, và tường lửa chặn mọi cổng khác. Kiểm chứng từ một máy thứ ba bằng curl/nc. Câu hỏi: khi bạn cố kết nối tới một cổng không mở (ví dụ 3306), phản hồi nhìn từ ngoài khác nhau thế nào giữa UFW (mặc định drop) và một cấu hình reject — và vì sao "im lặng" (drop) thường an toàn hơn "từ chối" (reject)?
