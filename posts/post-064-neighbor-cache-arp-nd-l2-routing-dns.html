Networking · Neighbor cache

Neighbor cache ARP/ND: phân biệt lỗi L2 neighbor với routing và DNS

Đọc neighbor cache theo đúng next hop để biết packet đang kẹt ở L2, route hay tên miền trước khi sửa cấu hình.

TRỤC · NETWORKINGĐỘ KHÓ · TRUNG CẤP~12 PHÚT
Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASELast verified: 2026-09-02

Mục tiêu

Xác định đúng next hop rồi dùng ARP/IPv6 Neighbor Discovery để chứng minh lỗi nằm ở L2 neighbor hay ở routing, firewall hoặc DNS.

Yêu cầu tiên quyết

  • Có một host hoặc gateway cùng link để kiểm tra, biết IP đích và interface đang dùng.
  • Ubuntu và Xubuntu dùng cùng nhóm lệnh iproute2; Debian và Fedora cũng dùng ip. FreeBSD dùng arp, ndp, route và ifconfig.
  • Các bước chính chỉ đọc trạng thái. Không flush neighbor cache trong bài này.
  • Dùng user thường; không cần sudo cho các lệnh quan sát bên dưới.

01 Bối cảnh thực tế

Một máy “không vào được mạng” có thể do nhiều lớp khác nhau. Nếu default gateway không resolve được MAC, sửa DNS không giúp gì. Ngược lại, neighbor cache tốt nhưng route sai thì flush ARP chỉ làm mất bằng chứng.

Với IPv4, neighbor cache trên Ethernet thường được gọi là ARP table. Với IPv6, Neighbor Discovery (ND) vừa ánh xạ địa chỉ IP sang link-layer address vừa theo dõi reachability của neighbor. Trên Linux, ip neigh hiển thị cả IPv4 và IPv6 neighbor; FreeBSD tách công cụ arp và ndp.

02 Kiến thức cốt lõi

  • Route quyết định next hop. Neighbor cache chỉ có ý nghĩa với neighbor trên link trực tiếp, thường là host cùng subnet hoặc gateway.
  • Neighbor resolution là bằng chứng adjacency. Linux có các trạng thái như REACHABLE, STALE, INCOMPLETE và FAILED. STALE không đồng nghĩa hỏng; FAILED sau probe thất bại mới là tín hiệu mạnh.
  • DNS là lớp khác. Nếu truy cập trực tiếp bằng IP cũng thất bại và next hop không resolve, ưu tiên xử lý neighbor/routing trước DNS.
  • Không flush theo phản xạ. Xóa cache có thể làm mất trạng thái hữu ích nhưng không sửa VLAN, Wi-Fi isolation, switch port, route hoặc firewall.

03 Các bước thực hiện

  1. 1. Xác định interface và next hop trước

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    ip -br link
ip route get <peer-ip>

    <peer-ip> là IP đích đang lỗi. Nếu đích không cùng subnet, neighbor cần kiểm thường là gateway mà ip route get trả về.

    FreeBSD — KHÁC Linux

    Run as: user

    ifconfig
route -n get <peer-ip>

  2. 2. Đọc neighbor cache hiện tại

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    ip neigh show dev <interface>
ip -6 neigh show dev <interface>

    FreeBSD — IPv4 ARP và IPv6 ND tách riêng

    Run as: user

    arp -an
ndp -an

    Tìm đúng next hop hoặc peer IP. Trên Linux, INCOMPLETE/FAILED đáng điều tra; STALE vẫn có thể là entry hợp lệ đang chờ xác nhận reachability.

  3. 3. Tạo một probe có giới hạn rồi đọc lại cache

    Mọi hệ

    Run as: user

    ping -c 2 <next-hop-or-peer-ip>

    Probe chỉ hai gói. Nếu peer chặn ICMP, ping thất bại chưa đủ để kết luận; hãy đọc neighbor cache ngay sau đó.

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    ip neigh get <next-hop-or-peer-ip> dev <interface>

    FreeBSD

    Run as: user

    arp -n <ipv4-neighbor>
ndp -n <ipv6-neighbor>

  4. 4. Tách lỗi neighbor khỏi routing và DNS

    • Nếu route chọn đúng interface/next hop nhưng neighbor không có link-layer address sau probe, điều tra link, VLAN, Wi-Fi isolation, peer state hoặc L2 filtering.
    • Nếu neighbor resolve thành MAC nhưng route get chọn sai gateway/interface, tập trung vào routing hoặc policy routing.
    • Nếu truy cập IP hoạt động nhưng hostname lỗi, lúc đó mới chuyển sang resolver/DNS.
    • Nếu neighbor và route đều hợp lý nhưng TCP/UDP vẫn lỗi, kiểm firewall và service path thay vì xóa neighbor cache.

04 Kiểm chứng

Kiểm lại ba lớp theo cùng một đích: route → neighbor → IP reachability. Không dùng hostname ở bước đầu để tránh trộn DNS vào bài test.

Ubuntu/Xubuntu · Debian · Fedora

Run as: user

ip route get <peer-ip>
ip neigh get <next-hop-or-peer-ip> dev <interface>

FreeBSD

Run as: user

route -n get <peer-ip>
arp -an
ndp -an

Expected Output / Kết quả mong đợi

  • Route hiển thị đúng interface và next hop dự kiến.
  • Neighbor trực tiếp có link-layer address; trên Linux không kết thúc ở FAILED sau probe.
  • Nếu IP path đã ổn nhưng tên miền vẫn lỗi, bằng chứng đủ để chuyển sang chẩn đoán DNS mà không sửa L2.

05 Lưu ý & Khắc phục lỗi

  • Không thấy entry không luôn là lỗi. Cache có thể chưa được populate hoặc đã hết tuổi. Tạo probe có giới hạn rồi đọc lại.
  • STALE không phải “dead”. Trên Linux, đây là trạng thái cache cần xác nhận lại khi traffic tiếp tục.
  • Gateway ngoài subnet không phải neighbor trực tiếp. Luôn dùng route để tìm next hop thực tế.
  • IPv6 không dùng ARP. Dùng ip -6 neigh trên Linux hoặc ndp trên FreeBSD.
  • Đừng flush toàn bảng để thử. Bài này cố ý chỉ đọc trạng thái; nếu sau này cần xóa một entry, ghi lại bằng chứng và chỉ tác động đúng target.

06 Bảo mật & vận hành

Neighbor cache có thể hé lộ IP và MAC trên segment nội bộ, vì vậy chỉ chia sẻ output cần thiết khi gửi ticket. Một mapping IP→MAC bất ngờ có thể là lỗi cấu hình, thiết bị đổi NIC, proxy ARP/ND hoặc dấu hiệu cần điều tra; không kết luận spoofing chỉ từ một snapshot.

07 Bài tập tự luyện

  1. Chọn một host cùng subnet và một host ngoài subnet. Dự đoán neighbor nào sẽ xuất hiện cho từng đích rồi kiểm bằng route và neighbor cache.
  2. Trên IPv6, so sánh output ip -6 neigh hoặc ndp -an trước và sau hai gói ping.
  3. Viết checklist ba dòng “route → neighbor → DNS” cho một incident thật và ghi bằng chứng nào cho phép chuyển sang lớp kế tiếp.
