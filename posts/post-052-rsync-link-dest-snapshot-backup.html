Storage · rsync snapshot-style backup

rsync snapshot-style backup với hard links và verification

Dùng --link-dest để mỗi phiên backup nhìn như một bản đầy đủ, trong khi file không đổi được hard-link về phiên trước và chỉ file thay đổi mới chiếm block mới.

TRỤC · STORAGEĐỘ KHÓ · TRUNG CẤP~12 PHÚT

Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASE

Last verified: 2026-08-21 · đối chiếu rsync upstream manual và FreeBSD rsync(1).

Mục tiêu

Tạo hai phiên backup bằng rsync --link-dest, chứng minh file không đổi dùng chung inode, file thay đổi tách inode, rồi kiểm checksum và restore.

Yêu cầu tiên quyết

  • Đã nắm filesystem/inode ở bài #024 và backup/restore ở #014/#021.
  • Có rsync trong PATH; bài không cài package và không sửa service hay cấu hình hệ thống.
  • Có shell user thường trên Ubuntu hoặc Xubuntu, Debian, Fedora hoặc FreeBSD và đủ dung lượng cho một lab nhỏ trong thư mục tạm.
  • Hai cây snapshot phải nằm trên cùng filesystem nếu muốn hard link hoạt động; hard link không vượt filesystem boundary.

01 Bối cảnh thực tế

Copy toàn bộ một cây dữ liệu mỗi ngày dễ hiểu nhưng tốn dung lượng. rsync --link-dest=<DIR> cho phép tạo một destination mới: file không đổi và có metadata phù hợp được hard-link từ cây tham chiếu, còn file mới hoặc thay đổi được truyền bình thường. Kết quả là mỗi thư mục snapshot có thể duyệt độc lập như một bản đầy đủ.

Đây không phải snapshot filesystem kiểu ZFS/Btrfs. Nó là một kỹ thuật backup ở mức file. Vì hard link dùng chung inode, sửa trực tiếp file bên trong một snapshot cũ có thể ảnh hưởng snapshot khác đang cùng trỏ vào inode đó. Vì vậy snapshot destination phải được xem là read-only về mặt vận hành.

02 Kiến thức cốt lõi

  • --link-dest: rsync tìm file không đổi trong directory tham chiếu và hard-link vào destination mới thay vì copy data block lại.
  • Destination mới: upstream khuyến nghị dùng --link-dest với cây đích mới/rỗng; tránh tiếp tục chỉnh file đã tồn tại trong snapshot.
  • Trailing slash: source/ nghĩa là copy nội dung của source vào destination; thiếu slash có thể thêm một tầng directory ngoài ý muốn.
  • Verification: cùng inode là bằng chứng hard link; checksum giống nhau là bằng chứng nội dung; restore test mới chứng minh bản backup dùng được.
  • Ubuntu/Xubuntu, Debian, Fedora: cùng dùng rsync upstream; khác biệt distro chủ yếu nằm ở package lifecycle, không ở semantics của --link-dest.
  • FreeBSD: rsync là tool userland/ports package, không dùng systemd; cú pháp --link-dest giữ cùng semantics theo rsync(1).

03 Các bước thực hiện

  1. Kiểm rsync và tạo lab tạm

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    rsync --version | head -n 1
lab="$(mktemp -d)"
mkdir -p "$lab/source" "$lab/snapshots"
printf 'stable-v1\n' > "$lab/source/config.ini"
printf 'data-v1\n' > "$lab/source/data.txt"

    FreeBSD

    Run as: user

    rsync --version | head -n 1
lab="$(mktemp -d)"
mkdir -p "$lab/source" "$lab/snapshots"
printf 'stable-v1\n' > "$lab/source/config.ini"
printf 'data-v1\n' > "$lab/source/data.txt"

    lab là directory tạm duy nhất của bài; mọi thao tác sau đều nằm dưới path này.

  2. Tạo snapshot đầu tiên

    Mọi hệ

    Run as: user

    rsync -a "$lab/source/" "$lab/snapshots/2026-08-20/"
find "$lab/snapshots/2026-08-20" -type f -maxdepth 1 -print

    Snapshot đầu chưa có basis directory nên là một copy đầy đủ ở mức file.

  3. Đổi một file nguồn và tạo snapshot thứ hai bằng link-dest

    Mọi hệ

    Run as: user

    printf 'data-v2\n' > "$lab/source/data.txt"
rsync -a --link-dest="$lab/snapshots/2026-08-20" \
  "$lab/source/" "$lab/snapshots/2026-08-21/"

    config.ini không đổi nên đủ điều kiện để hard-link; data.txt thay đổi nên snapshot mới phải có inode riêng.

  4. Kiểm hard link bằng inode và link count

    Mọi hệ

    Run as: user

    ls -li "$lab/snapshots/2026-08-20/config.ini" "$lab/snapshots/2026-08-21/config.ini"
ls -li "$lab/snapshots/2026-08-20/data.txt" "$lab/snapshots/2026-08-21/data.txt"

    Kỳ vọng: hai path config.ini có cùng inode; hai path data.txt có inode khác nhau.

  5. Kiểm checksum theo hệ điều hành

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    sha256sum "$lab/source/config.ini" "$lab/snapshots/2026-08-21/config.ini"
sha256sum "$lab/source/data.txt" "$lab/snapshots/2026-08-21/data.txt"

    FreeBSD

    Run as: user

    sha256 "$lab/source/config.ini" "$lab/snapshots/2026-08-21/config.ini"
sha256 "$lab/source/data.txt" "$lab/snapshots/2026-08-21/data.txt"

    Trong từng cặp, digest phải giống nhau.

  6. Restore snapshot mới sang cây riêng và so sánh

    Mọi hệ

    Run as: user

    mkdir "$lab/restore"
rsync -a "$lab/snapshots/2026-08-21/" "$lab/restore/"
cmp "$lab/source/config.ini" "$lab/restore/config.ini"
cmp "$lab/source/data.txt" "$lab/restore/data.txt"

    cmp im lặng và exit 0 cho cả hai file là bằng chứng restore khớp nguồn hiện tại của lab.

04 Kiểm chứng

Expected Output / Kết quả mong đợi:

  • rsync hoàn tất không lỗi.
  • Hai config.ini ở snapshot 20/08 và 21/08 có cùng inode; link count thường tăng vì cùng inode có nhiều tên.
  • Hai data.txt có inode khác nhau sau khi nguồn thay đổi.
  • Checksum của source và snapshot 21/08 giống nhau cho từng file.
  • Hai lệnh cmp sau restore exit 0.

Run as: user

test -f "$lab/restore/config.ini"
test -f "$lab/restore/data.txt"
cmp "$lab/source/config.ini" "$lab/restore/config.ini"
cmp "$lab/source/data.txt" "$lab/restore/data.txt"

05 Lưu ý & Khắc phục lỗi

  • File không hard-link: kiểm hai snapshot có cùng filesystem, ownership/permission/timestamp có phù hợp và --link-dest có trỏ đúng basis directory.
  • Thừa một tầng directory: kiểm trailing slash ở source. source/ và source có semantics khác nhau.
  • Destination đã tồn tại: ưu tiên một directory mới/rỗng cho từng phiên. Reuse destination làm semantics khó kiểm và có thể tác động attribute của hard-linked file.
  • Không dùng --inplace theo phản xạ: với cây snapshot hard-linked, sửa trực tiếp inode dùng chung làm tăng rủi ro phá tính bất biến của phiên cũ.
  • Rsync thành công nhưng backup chưa đáng tin: thêm checksum và restore test; exit code của lệnh copy chỉ là một lớp bằng chứng.

06 Bảo mật & vận hành

Đặt snapshot directory ở nơi user/service backup có quyền ghi nhưng workload nguồn không có quyền sửa. Sau khi một phiên hoàn tất, coi nội dung của phiên đó là immutable về mặt quy trình. Nếu cần retention, chỉ xoá cả snapshot directory đã hết hạn sau khi xác nhận target; không sửa từng file bên trong snapshot cũ.

Với dữ liệu production, bổ sung kiểm soát consistency ở tầng ứng dụng trước rsync. --link-dest không tự tạo transaction boundary cho database hoặc ứng dụng đang ghi liên tục; snapshot-style ở mức file không thay thế application-consistent backup.

07 Bài tập tự luyện

  1. Thêm file thứ ba không đổi qua ba phiên và quan sát inode/link count.
  2. Tạo một snapshot mới sau khi đổi permission của file nhưng không đổi nội dung; quan sát khi nào rsync không còn hard-link do preserved attributes khác.
  3. So sánh tổng dung lượng của toàn cây snapshots với việc copy ba bản độc lập.
  4. Viết checklist retention yêu cầu verify target trước khi xoá một snapshot hết hạn.
