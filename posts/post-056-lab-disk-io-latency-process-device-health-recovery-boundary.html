Lab disk I/O latency: process, device health và recovery boundary

Tạo I/O pressure có giới hạn trên file lab, xác định process gây tải, kiểm tra device health và chọn recovery boundary trước khi thay đổi storage.

TRỤC · ÔN TẬPĐỘ KHÓ · NÂNG CAO~20 PHÚT
Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASELast verified: 2026-08-25

Mục tiêu

Phân biệt workload gây I/O, device có dấu hiệu suy giảm và filesystem pressure; sau đó chọn recovery boundary dựa trên bằng chứng thay vì sửa storage theo phản xạ.

Yêu cầu tiên quyết

  • Host lab dùng riêng, có ít nhất 1 GiB trống trong /var/tmp; không chạy failure injection trên production, VM shared hoặc storage đang phục vụ workload thật.
  • Đã đọc #019, #024, #026, #033, #038 và #040 để hiểu CPU/RAM/I/O baseline, filesystem capacity, process ownership và disk health.
  • Ubuntu hoặc Xubuntu, Debian và Fedora dùng Linux device model; FreeBSD dùng GEOM và công cụ BSD riêng.
  • Cần quyền sudo/root để cài tool và đọc health của device; workload fio chạy bằng user thường trên file lab, không ghi raw device.

01 Bối cảnh thực tế

Ứng dụng phản hồi chậm, load tăng và người vận hành thấy storage busy. Ba nguyên nhân có thể cho triệu chứng gần giống nhau: một process đang tạo quá nhiều I/O, device bắt đầu lỗi, hoặc filesystem bị pressure do capacity/writeback. Chọn sai boundary dễ dẫn tới restart vô ích, thay disk nhầm hoặc chạy repair khi chưa có backup.

Lab này chỉ inject resource pressure có giới hạn bằng một file trong /var/tmp. Không inject media error, không benchmark raw device và không cố làm đầy filesystem.

Topology lab

  • observer-shell: terminal theo dõi process, device latency, health và kernel/system log.
  • io-target: cùng host lab nhưng là file riêng /var/tmp/linux-daily-056/io-test.bin; đây là blast radius duy nhất của failure injection.
  • Không dùng mount production, volume database, root filesystem gần đầy hoặc shared SAN/NAS làm target.

Safety boundary

  • Kiểm tra dung lượng trước khi tạo file. Nếu /var/tmp còn dưới 1 GiB, dừng lab.
  • Workload có timeout 30 giây, file tối đa 256 MiB, chỉ 2 jobs và không dùng raw block device.
  • Nếu SMART/health báo lỗi hoặc log xuất hiện media/controller error mới, dừng fio ngay và chuyển sang backup/evacuation; không tiếp tục stress.
  • Ghi baseline trước failure injection để có điểm so sánh. Một con số latency đơn lẻ không đủ để kết luận.

02 Kiến thức cốt lõi

  • Process evidence: xác định workload nào tạo read/write thay vì suy từ tên service.
  • Device evidence: queue/latency/utilization cho biết device đang bận; health/log cho biết có dấu hiệu lỗi phần cứng hay controller hay không.
  • Filesystem evidence: capacity, inode và lỗi filesystem có thể làm ứng dụng chậm dù SMART vẫn sạch.
  • Recovery boundary: workload-bound → throttle/stop workload; device-health-bound → bảo toàn dữ liệu và thay device; filesystem-bound → xử lý capacity/integrity theo đúng filesystem.

SMART “PASSED” không chứng minh device nhanh hoặc hoàn toàn khỏe. Ngược lại, latency cao trong lúc workload cố ý chạy không chứng minh phần cứng hỏng.

03 Các bước thực hiện

  1. Cài tool quan sát trên host lab

    Ubuntu / Xubuntu / Debian

    Run as: sudo

    sudo apt update
sudo apt install -y fio sysstat smartmontools

    Fedora

    Run as: sudo

    sudo dnf install -y fio sysstat smartmontools

    FreeBSD

    Run as: root

    pkg install -y fio smartmontools

    FreeBSD đã có iostat, gstat và procstat trong base system; không dùng apt, dnf hoặc systemctl.

  2. Xác định filesystem và device chứa target

    Ubuntu / Xubuntu / Debian / Fedora

    Run as: user

    df -h /var/tmp
findmnt -T /var/tmp -o SOURCE,TARGET,FSTYPE,OPTIONS
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS

    FreeBSD

    Run as: root

    df -h /var/tmp
mount
gpart show

    Expected Output: xác định được filesystem của /var/tmp và device bên dưới. Chỉ tiếp tục khi còn ít nhất 1 GiB trống.

  3. Ghi baseline trước khi tạo pressure

    Linux

    Run as: user

    iostat -xz 1 5
vmstat 1 5

    FreeBSD

    Run as: root

    iostat -x -w 1 -c 5
gstat -p -I 1s

    Với gstat, quan sát vài chu kỳ rồi nhấn q. Ghi lại device đang chứa target, latency và busy percentage trước failure injection.

  4. Kiểm tra device health trước khi stress

    Linux

    Run as: sudo

    sudo smartctl --scan-open
sudo smartctl -H -A /dev/<device>

    Thay <device> bằng device đã inventory, ví dụ sda hoặc device NVMe phù hợp. Đây là lệnh đọc; không dùng placeholder này cho lệnh phá hủy.

    FreeBSD

    Run as: root

    smartctl --scan-open
smartctl -H -A /dev/<device>

    Trên FreeBSD, device có thể là ada0, da0 hoặc NVMe tương ứng. Nếu health không sạch hoặc có media error, dừng lab.

Failure injection — tạo I/O pressure có giới hạn

Mọi hệ

Run as: user

mkdir -p /var/tmp/linux-daily-056
fio --name=linux-daily-056 \
  --filename=/var/tmp/linux-daily-056/io-test.bin \
  --size=256m --rw=randwrite --bs=4k --iodepth=8 --numjobs=2 \
  --direct=1 --runtime=30 --time_based --group_reporting \
  --output=/var/tmp/linux-daily-056/fio.txt &
echo $! > /var/tmp/linux-daily-056/fio.pid

Expected failure state: trong tối đa 30 giây, device latency/queue tăng so với baseline và process fio xuất hiện như nguồn I/O. Nếu host mất responsiveness hoặc log báo lỗi device, dừng workload bằng PID đã lưu.

04 Kiểm chứng

Linux — process + device evidence

Run as: sudo

pidstat -d -C fio 1 5
iostat -xz 1 5
sudo dmesg --level=err,warn | tail -n 30

FreeBSD — process + device evidence

Run as: root

procstat -r "$(pgrep -n fio)"
iostat -x -w 1 -c 5
gstat -p -I 1s

Expected Output / Kết quả mong đợi:

  • Observability: process fio có block I/O; device chứa /var/tmp thể hiện pressure cao hơn baseline trong cửa sổ 30 giây.
  • Negative: không có media/controller error mới; SMART/health không chuyển sang trạng thái xấu chỉ vì workload synthetic.
  • Functional: workload tự kết thúc theo timeout và file output fio.txt ghi kết quả hoàn chỉnh.
  • Recovery: sau khi fio kết thúc, rerun iostat/gstat; queue/latency phải trở về gần baseline và không còn process stressor.

Mọi hệ — xác nhận stressor đã dừng

Run as: user

wait "$(cat /var/tmp/linux-daily-056/fio.pid)" 2>/dev/null || true
pgrep -af fio || true
cat /var/tmp/linux-daily-056/fio.txt | tail -n 20

Gỡ / Hoàn tác

Nếu cần dừng sớm, chỉ kill đúng PID đã lưu; không dùng killall fio trên host có workload khác.

Mọi hệ

Run as: user

test -f /var/tmp/linux-daily-056/fio.pid && kill "$(cat /var/tmp/linux-daily-056/fio.pid)" 2>/dev/null || true
pgrep -af fio || true

Sau rollback, lặp lại baseline. Nếu latency vẫn cao khi stressor đã dừng, boundary không còn là workload lab; chuyển sang kiểm device/filesystem thay vì chạy lại stress.

Cleanup

Mọi hệ

Run as: user

pgrep -af fio || true
rm -f /var/tmp/linux-daily-056/io-test.bin /var/tmp/linux-daily-056/fio.txt /var/tmp/linux-daily-056/fio.pid
rmdir /var/tmp/linux-daily-056 2>/dev/null || true

⚠️ Lệnh rm chỉ nhắm đúng ba file lab trong thư mục cố định. Xác nhận đường dẫn là /var/tmp/linux-daily-056 trước khi chạy.

Nếu fio, sysstat hoặc smartmontools đã tồn tại trước lab thì giữ nguyên. Chỉ gỡ package khi bạn chắc chắn chúng được cài riêng cho bài này.

05 Lưu ý & Khắc phục lỗi

  • direct=1 không được filesystem hỗ trợ: bỏ --direct=1, ghi rõ rằng page cache tham gia và không so số liệu với lần direct I/O.
  • Latency cao nhưng SMART sạch: kiểm process, queue, virtualized storage và backend shared. SMART sạch không loại trừ contention.
  • SMART báo lỗi hoặc kernel log có I/O error: dừng benchmark. Ưu tiên backup/evacuation và thay device theo maintenance window.
  • Filesystem gần đầy/inode cạn: quay lại #024; đừng tăng fio size để “test thêm”.
  • Không thấy process nhưng device vẫn busy: có thể I/O đến từ kernel, VM khác hoặc storage backend. Thu thêm evidence trước khi restart service.

06 Bảo mật & vận hành

Disk health output có serial/model và topology thiết bị; che thông tin nhận dạng khi đưa vào ticket công khai. Không chạy stressor trên volume chứa database, hypervisor datastore hoặc backup repository đang hoạt động.

Recovery boundary nên được ghi vào incident timeline: workload-bound, filesystem-bound, device-health-bound hoặc chưa đủ bằng chứng. Chỉ boundary cuối cùng mới quyết định restart, cleanup, repair hay thay phần cứng.

07 Bài tập tự luyện

  1. Ghi baseline 5 mẫu rồi chạy lab. So sánh latency trước/trong/sau và giải thích vì sao một spike đơn lẻ chưa đủ kết luận.
  2. Giả lập ca “process-bound”: giữ device health sạch, chỉ tăng workload; viết recovery plan không đụng filesystem repair.
  3. Đọc một SMART report mẫu có warning và viết boundary mới: hành động nào phải dừng, dữ liệu nào cần bảo toàn trước.
  4. Trên FreeBSD, đối chiếu iostat với gstat; trên Linux, đối chiếu pidstat với iostat. Ghi điểm mà process evidence và device evidence bổ sung cho nhau.
