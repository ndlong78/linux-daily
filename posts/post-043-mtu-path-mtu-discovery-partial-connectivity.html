Networking · MTU / PMTUD

MTU và Path MTU Discovery: chẩn đoán kết nối treo một phần

Dùng probe có kiểm soát để xác định khi đường truyền chỉ hỏng với packet lớn và tách lỗi MTU/PMTUD khỏi DNS, route hoặc firewall.

TRỤC · NETWORKINGĐỘ KHÓ · TRUNG BÌNH~12 PHÚT

Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASE

Last verified: 2026-08-12 · đối chiếu RFC, manpage iputils và FreeBSD; các lệnh trong bài chỉ đọc/probe, không đổi cấu hình host.

Mục tiêu

Xác định một lỗi kết nối treo với payload lớn có liên quan MTU/PMTUD hay không trước khi thay đổi interface, route hoặc firewall.

Yêu cầu tiên quyết

  • Đã nắm các bài #008, #022, #029 và #036.
  • Có một đích IPv4 thật sự đi qua đường mạng cần kiểm tra.
  • Có lệnh ping; Linux dùng iputils, FreeBSD dùng ping(8) trong base system.
  • Biết MTU của interface đầu ra hoặc có quyền đọc bằng ip link/ifconfig.

01 Bối cảnh thực tế

DNS có thể resolve đúng, route có thể tồn tại và ping mặc định vẫn trả lời nhưng HTTPS, SSH sau handshake hoặc truyền file lại đứng. Một nguyên nhân điển hình là packet lớn không đi qua được đường hẹp hơn. Nếu ICMP báo cần giảm kích thước bị chặn, PMTUD không học được giới hạn mới và kết nối có thể treo một phần.

02 Kiến thức cốt lõi

  • Link MTU là giới hạn của một link cục bộ. Path MTU là MTU nhỏ nhất trên toàn bộ path.
  • IPv4 PMTUD theo RFC 1191 dựa vào packet không được fragment và ICMP báo packet quá lớn/fragmentation needed.
  • IPv6 không cho router fragment packet. RFC 8201 dùng ICMPv6 Packet Too Big để source giảm kích thước gửi.
  • Với IPv4 không có IP options, payload ICMP 1472 tạo packet IP 1500 byte: 20 byte IPv4 header + 8 byte ICMP header + 1472 byte payload.
  • Một probe lớn thất bại chưa đủ kết luận firewall hay MTU. So sánh nhiều kích thước trên cùng đích và cùng path.

03 Các bước thực hiện

  1. Xác định interface và MTU đầu ra.

    Ubuntu/Xubuntu, Debian và Fedora — chạy bằng user thường.

    Run as: user

    ip route get <target-ipv4>
ip link show

    <target-ipv4> là địa chỉ IPv4 của server đang gặp hiện tượng treo. Ghi lại interface được route chọn và giá trị mtu của interface đó.

    FreeBSD

    Chạy bằng user thường.

    Run as: user

    route -n get <target-ipv4>
ifconfig

    Ghi lại interface đi ra và MTU hiển thị bởi ifconfig.

  2. Kiểm tra reachability bằng packet nhỏ.

    Tất cả hệ — chạy bằng user thường.

    Run as: user

    ping -4 -c 3 <target-ipv4>

    Nếu packet nhỏ cũng không tới đích, chưa nên tập trung vào MTU. Quay lại DNS, route, ARP/NDP và firewall theo các bài prerequisite.

  3. Probe packet tương đương MTU 1500 trên Linux.

    Ubuntu/Xubuntu, Debian và Fedora — chạy bằng user thường. -M do yêu cầu kernel không fragment packet IPv4.

    Run as: user

    ping -4 -M do -s 1472 -c 3 <target-ipv4>

    Nếu path nhỏ hơn 1500, có thể thấy lỗi kiểu message too long, ICMP fragmentation-needed, hoặc probe timeout nếu ICMP cần thiết bị chặn.

  4. Probe cùng kích thước trên FreeBSD.

    FreeBSD — chạy bằng user thường. -D disable fragmentation cho IPv4.

    Run as: user

    ping -4 -D -s 1472 -c 3 <target-ipv4>

    Không thay -D bằng option Linux -M do.

  5. Giảm payload để tìm ngưỡng hoạt động.

    Linux — chạy bằng user thường.

    Run as: user

    ping -4 -M do -s 1400 -c 3 <target-ipv4>
ping -4 -M do -s 1372 -c 3 <target-ipv4>

    FreeBSD

    Chạy bằng user thường.

    Run as: user

    ping -4 -D -s 1400 -c 3 <target-ipv4>
ping -4 -D -s 1372 -c 3 <target-ipv4>

    Nếu 1472 thất bại nhưng kích thước nhỏ hơn ổn định, đã có bằng chứng mạnh về giới hạn kích thước trên path. Không tự động đổi MTU chỉ từ một phép thử.

  6. Đối chiếu packet capture nếu kết quả còn mơ hồ.

    Chạy capture theo bài #036 trên đúng interface và chỉ trong thời gian ngắn. Tìm ICMP IPv4 fragmentation-needed hoặc ICMPv6 Packet Too Big. Nếu không thấy phản hồi ICMP nhưng packet lớn liên tục biến mất, kiểm tra firewall/tunnel ở các hop trung gian trước khi sửa endpoint.

04 Kiểm chứng

Chạy lại cùng đích với một payload nhỏ và một payload lớn. Giữ nguyên source, route và thời điểm kiểm tra để so sánh có ý nghĩa.

Linux — chạy bằng user thường.

Run as: user

ping -4 -M do -s 1200 -c 3 <target-ipv4>
ping -4 -M do -s 1472 -c 3 <target-ipv4>

FreeBSD

Chạy bằng user thường.

Run as: user

ping -4 -D -s 1200 -c 3 <target-ipv4>
ping -4 -D -s 1472 -c 3 <target-ipv4>

Expected Output / Kết quả mong đợi

  • Nếu cả hai kích thước thành công ổn định, chưa có bằng chứng path đang chặn packet 1500-byte theo probe này.
  • Nếu 1200 thành công nhưng 1472 thất bại lặp lại trên cùng path, ghi nhận ngưỡng kích thước và tiếp tục xác định hop/tunnel gây co MTU.
  • Nếu nhận được ICMP fragmentation-needed hoặc Packet Too Big, lưu lại MTU được báo và đối chiếu với tunnel/VPN/VLAN đang đi qua.

05 Lưu ý & Khắc phục lỗi

  • Ping nhỏ chạy không chứng minh TCP payload lớn sẽ chạy. Ping mặc định chỉ dùng payload nhỏ.
  • 1472 chỉ tương ứng packet IPv4 1500 byte khi không có IP options. Encapsulation như GRE, VXLAN, IPsec hoặc WireGuard có thể làm PMTU nhỏ hơn MTU vật lý.
  • Timeout không tự động đồng nghĩa PMTUD black hole. ICMP Echo có thể bị lọc riêng. Cần kết hợp packet capture và triệu chứng ứng dụng.
  • Không hạ MTU trên toàn host theo phỏng đoán. Xác định đúng path, tunnel và overhead trước khi thay đổi cấu hình.

06 Bảo mật & vận hành

  • Giới hạn số probe bằng -c; không flood ping trên mạng production.
  • ICMP Packet Too Big/fragmentation-needed là tín hiệu vận hành cần thiết cho PMTUD. Không chặn toàn bộ ICMP theo phản xạ.
  • Với đường nhiều tunnel, ghi lại source/destination, interface và thời điểm capture để tránh kết luận từ path khác.
  • Bài này chỉ quan sát. Nếu phải đổi MTU, firewall hoặc tunnel config, tạo change riêng có rollback và verification.

07 Bài tập tự luyện

Chọn một host lab đi qua VPN hoặc tunnel. Ghi MTU interface, thử ba payload IPv4 khác nhau với fragmentation bị vô hiệu hóa, rồi lập bảng kích thước → thành công/thất bại. Giải thích vì sao kết quả đó chưa đủ để xác định chính xác hop gây giới hạn nếu chưa có packet capture.
