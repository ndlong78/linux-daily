Bảo mật · OpenSSH user certificates

OpenSSH certificates: user CA, validity interval và thu hồi credential

Dùng OpenSSH user certificate để tách trust khỏi authorized_keys tĩnh, giới hạn thời hạn credential và thu hồi bằng KRL có kiểm chứng.

TRỤC · BẢO MẬTĐỘ KHÓ · NÂNG CAO~14 PHÚT
Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASELast verified: 2026-08-27

Mục tiêu

Cấu hình một user CA cho OpenSSH, phát hành certificate ngắn hạn theo principal, kiểm tra thời hạn rồi thu hồi credential bằng KRL mà không quay lại quản lý từng public key trên từng host.

Yêu cầu tiên quyết

  • Đã nắm SSH key-only ở #002, least privilege ở #023 và audit đăng nhập ở #030.
  • Một host quản trị giữ CA private key và một server lab; không đặt CA private key trên SSH server.
  • Giữ một phiên quản trị dự phòng hoặc console trước khi reload sshd.
  • Ubuntu hoặc Xubuntu, Debian, Fedora và FreeBSD đều có OpenSSH; service command khác nhau giữa Linux và FreeBSD.

01 Bối cảnh thực tế

authorized_keys tĩnh phù hợp quy mô nhỏ nhưng tạo toil khi một người cần truy cập nhiều host hoặc khi credential phải hết hạn nhanh. OpenSSH user certificate chuyển trust sang CA: server giữ CA public key, còn client trình public key kèm certificate đã được CA ký.

Certificate không tự giải quyết mọi bài toán thu hồi. Thời hạn ngắn giảm cửa sổ rủi ro; khi cần chặn trước hạn, OpenSSH hỗ trợ Key Revocation List (KRL) và directive RevokedKeys.

02 Kiến thức cốt lõi

  • ssh-keygen -s ký public key thành certificate; -n đặt principal, -V đặt validity interval và -z đặt serial khác 0.
  • TrustedUserCAKeys trỏ tới file chứa CA public key mà sshd tin để xác thực user certificate.
  • Certificate dùng với TrustedUserCAKeys phải có principal; principal phải khớp user được phép đăng nhập.
  • ssh-keygen -k tạo KRL; RevokedKeys làm sshd từ chối key/certificate có trong danh sách thu hồi.
  • CA private key là credential có blast radius lớn. Giữ nó tách khỏi server và bảo vệ bằng passphrase hoặc HSM/agent phù hợp.

03 Các bước thực hiện

  1. Tạo user CA trên host quản trị

    Host quản trị — mọi hệ

    Run as: user

    ssh-keygen -t ed25519 -f ./user_ca -C "linux-daily-058-user-ca"

    Đặt passphrase mạnh khi được hỏi. Chỉ phân phối user_ca.pub; không copy file private user_ca sang server.

  2. Tạo key client và ký certificate ngắn hạn

    Host quản trị / client

    Run as: user

    ssh-keygen -t ed25519 -f ./id_ed25519_ld058 -C "linux-daily-058-client"
ssh-keygen -s ./user_ca -I ld058-user-001 -n <username> -V -5m:+1h -z 1001 ./id_ed25519_ld058.pub
ssh-keygen -L -f ./id_ed25519_ld058-cert.pub

    Thay <username> bằng tài khoản lab trên server. Khoảng bắt đầu sớm 5 phút giảm lỗi do clock skew nhỏ; certificate hết hạn sau 1 giờ.

  3. Cài CA public key và cấu hình trust

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: sudo

    sudo install -m 0644 <ca-public-key-file> /etc/ssh/trusted-user-ca-keys.pem
sudo sshd -t

    FreeBSD — rc.d, không dùng systemd

    Run as: root

    install -m 0644 <ca-public-key-file> /etc/ssh/trusted-user-ca-keys.pem
sshd -t

    Thay <ca-public-key-file> bằng đường dẫn local tới bản sao của user_ca.pub. Thêm dòng sau vào /etc/ssh/sshd_config rồi chạy lại sshd -t:

    TrustedUserCAKeys /etc/ssh/trusted-user-ca-keys.pem

  4. Reload sshd theo từng hệ

    Ubuntu/Xubuntu · Debian

    Run as: sudo

    sudo systemctl reload ssh

    Fedora

    Run as: sudo

    sudo systemctl reload sshd

    FreeBSD

    Run as: root

    service sshd reload

  5. Tạo KRL khi cần thu hồi trước hạn

    Host quản trị

    Run as: user

    ssh-keygen -k -f ./revoked-user-keys.krl ./id_ed25519_ld058-cert.pub
ssh-keygen -Q -f ./revoked-user-keys.krl ./id_ed25519_ld058-cert.pub

    Expected Output: lệnh -Q báo certificate đã bị revoked.

    Chuyển KRL sang server qua kênh quản trị an toàn, cài thành /etc/ssh/revoked-user-keys.krl, thêm RevokedKeys /etc/ssh/revoked-user-keys.krl vào sshd_config, chạy sshd -t rồi reload theo đúng nhánh OS ở bước trước.

04 Kiểm chứng

Client

Run as: user

ssh -i ./id_ed25519_ld058 -o CertificateFile=./id_ed25519_ld058-cert.pub <username>@<server-ip> true

Thay hai placeholder bằng user principal và IP server lab.

Expected Output / Kết quả mong đợi

  • Trước khi thu hồi: lệnh thoát mã 0 và không in output.
  • Sau khi KRL được cài + reload: cùng certificate bị từ chối xác thực.
  • Sau khi quá validity interval: certificate cũng bị từ chối dù không có trong KRL.

Gỡ / Hoàn tác

Giữ phiên quản trị dự phòng đang mở. Xóa hai directive TrustedUserCAKeys và RevokedKeys khỏi /etc/ssh/sshd_config, chạy sshd -t, reload đúng service theo OS, rồi xóa /etc/ssh/trusted-user-ca-keys.pem và /etc/ssh/revoked-user-keys.krl nếu chúng chỉ phục vụ lab. Không xóa CA private key nếu nó còn được dùng ở môi trường khác.

05 Lưu ý & Khắc phục lỗi

  • Certificate có CA đúng nhưng principal sai vẫn bị từ chối. Kiểm bằng ssh-keygen -L.
  • Clock lệch có thể làm certificate trông như chưa có hiệu lực hoặc đã hết hạn; sửa time sync thay vì kéo validity quá dài.
  • Nếu file RevokedKeys được cấu hình nhưng không đọc được, public-key authentication có thể bị từ chối rộng hơn dự kiến. Validate path và permission trước reload.
  • Không thay KRL bằng cách sửa binary file tại chỗ. Tạo file mới rồi cài/replace hoàn chỉnh.

06 Bảo mật & vận hành

  • Đặt CA private key ngoài SSH server; giới hạn người/quy trình có quyền ký.
  • Dùng serial khác 0 và key ID có ý nghĩa để audit/revoke theo sự kiện.
  • Ưu tiên certificate ngắn hạn; KRL là đường thu hồi khẩn cấp, không phải lý do để cấp validity dài.
  • Không bật certificate trust trên fleet trước khi có inventory host, rollback và cách phân phối CA/KRL nhất quán.

07 Bài tập tự luyện

  1. Phát hành hai certificate cho cùng public key với serial 1001 và 1002, validity khác nhau.
  2. Thu hồi chỉ certificate serial 1001 bằng KRL và chứng minh serial 1002 vẫn đăng nhập được.
  3. Đổi principal sang một user khác và dùng ssh-keygen -L để giải thích vì sao login ban đầu fail.
