Networking · DNS troubleshooting

DNS lỗi ở đâu? Tách client, resolver và authoritative bằng dig, resolvectl, drill

DNS hỏng thường bị báo thành 'mất mạng', nhưng lỗi có thể nằm ở NSS của ứng dụng, resolver cục bộ, DNS server được cấp qua DHCP/VPN hoặc chuỗi authoritative. Bài này đi từ client ra ngoài theo từng lớp để khoanh vùng trước khi sửa.

TRỤC · NETWORKINGĐỘ KHÓ · TRUNG CẤP~12 PHÚT

Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.3-RELEASE

Last verified: 2026-08-09 · đối chiếu tài liệu official/upstream

Mục tiêu

Khoanh vùng lỗi DNS theo client, resolver và authoritative thay vì sửa cấu hình theo cảm tính.

Yêu cầu tiên quyết

Một hostname kiểm thử và resolver dự kiến; thao tác chính read-only.

01 Bối cảnh thực tế

Một host vẫn ping được gateway và IP Internet nhưng apt, dnf, trình duyệt hoặc service discovery báo “name or service not known”. Một tình huống khác: tên public phân giải được nhưng zone nội bộ qua VPN lại không. Cả hai đều là “DNS lỗi” ở góc nhìn người dùng, nhưng cách sửa hoàn toàn khác.

Mục tiêu của triage là trả lời lần lượt: ứng dụng có resolve qua NSS được không; máy đang dùng resolver nào; truy vấn DNS trực tiếp có nhận phản hồi không; và chỉ khi cần mới trace chuỗi authoritative.

02 Kiến thức cốt lõi

  • getent và dig/drill không trả lời cùng một câu hỏi. getent hosts đi qua cơ chế NSS của hệ điều hành, nên có thể thấy dữ liệu từ /etc/hosts hoặc resolver tích hợp. dig/drill gửi DNS query và phù hợp để tách lỗi DNS khỏi NSS.
  • Resolver runtime có thể khác nội dung bạn tưởng đang nằm trong /etc/resolv.conf. Máy dùng systemd-resolved có DNS theo từng link, search domain và split DNS; resolvectl status cho biết trạng thái global/per-link đang hiệu lực.
  • Query mặc định và query tới server chỉ định là hai phép thử khác nhau. dig example.com A dùng resolver được cấu hình; dig @SERVER example.com A kiểm trực tiếp server đó. FreeBSD dùng cú pháp drill example.com @SERVER A.
  • +trace/-T không phải phép thử đầu tiên. Trace đi từ root xuống authoritative và không kiểm đúng đường recursive resolver mà ứng dụng đang dùng; firewall doanh nghiệp cũng có thể chặn DNS trực tiếp ra ngoài.
  • Phân biệt kết quả: timeout thường hướng tới reachability/firewall/server không trả lời; NXDOMAIN nghĩa là server đã trả lời rằng tên không tồn tại; SERVFAIL cần điều tra server-side, delegation hoặc validation thay vì đổi DNS mù quáng.

03 Các bước thực hiện

  1. Kiểm phân giải qua NSS để xác nhận triệu chứng.
  2. Xác định resolver runtime thật sự đang dùng.
  3. Query trực tiếp resolver bằng dig/drill.
  4. Khi cần, lần theo authoritative chain để xác định lớp lỗi.

Ví dụ dùng domain public dành cho tài liệu là example.com. Với DNS nội bộ, thay bằng FQDN thật nhưng không gửi tên nội bộ tới public resolver.

Ubuntu / Xubuntu — APT + systemd-resolved

Run as: user

sudo apt update
sudo apt install -y dnsutils

getent hosts example.com
if systemctl is-active --quiet systemd-resolved; then
  resolvectl status
  resolvectl query example.com
else
  cat /etc/resolv.conf
fi

dig example.com A
Debian — APT; không giả định systemd-resolved đang được dùng

Run as: user

sudo apt update
sudo apt install -y dnsutils

getent hosts example.com
cat /etc/resolv.conf
if systemctl is-active --quiet systemd-resolved; then
  resolvectl status
  resolvectl query example.com
fi

dig example.com A

Khác biệt: đừng cài hoặc bật systemd-resolved chỉ để troubleshooting trên Debian. Trước hết phải quan sát resolver hiện có; thay backend DNS là một thay đổi cấu hình, không phải phép đo.

Fedora — DNF + systemd-resolved

Run as: user

sudo dnf install -y bind-utils

getent hosts example.com
if systemctl is-active --quiet systemd-resolved; then
  resolvectl status
  resolvectl query example.com
else
  cat /etc/resolv.conf
fi

dig example.com A
FreeBSD — drill/LDNS utilities, không systemd

Run as: root

getent hosts example.com
cat /etc/resolv.conf

drill example.com A

DNS_SERVER=$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)
if [ -n "$DNS_SERVER" ]; then
  drill example.com @"$DNS_SERVER" A
fi

FreeBSD không có resolvectl hay systemd. /etc/resolv.conf có thể được cập nhật bởi DHCP/resolvconf; hãy truy nguồn cấu hình trước khi sửa file trực tiếp.

04 Kiểm chứng

Kết quả mong đợi

  • Xác định được resolver và DNS status cụ thể.
  • NSS và direct query nhất quán hoặc chỉ ra rõ điểm khác nhau.
  • Nếu authoritative lỗi, direct query tới authoritative tái hiện được lỗi.

Bước 1 — NSS/application:

Run as: user

getent hosts example.com

Bước 2 — DNS query mặc định:

Run as: user

# Linux
DIG_DOMAIN=example.com
dig "$DIG_DOMAIN" A

# FreeBSD
drill example.com A

Bước 3 — hỏi đúng nameserver đang thấy trong resolv.conf:

Run as: user

# Linux
DNS_SERVER=$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)
[ -n "$DNS_SERVER" ] && dig @"$DNS_SERVER" example.com A

# FreeBSD
DNS_SERVER=$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)
[ -n "$DNS_SERVER" ] && drill example.com @"$DNS_SERVER" A

Nếu Linux trả về 127.0.0.53, bạn đang kiểm local systemd-resolved stub. Hãy dùng resolvectl status để xem upstream DNS theo từng link thay vì coi địa chỉ stub là DNS server cuối cùng.

Bước 4 — chỉ khi cần kiểm delegation/authoritative:

Run as: user

# Linux
dig +trace example.com A

# FreeBSD
drill -T example.com A

Bước 5 — nghi UDP/fragmentation/truncation:

Run as: user

# Linux
dig +tcp example.com A

# FreeBSD
drill -t example.com A

05 Lưu ý & Khắc phục lỗi

  • dig chạy được nhưng ứng dụng vẫn lỗi: kiểm getent, /etc/nsswitch.conf, search domain và split DNS. DNS query trực tiếp không chứng minh toàn bộ NSS path của ứng dụng ổn.
  • Sửa thẳng /etc/resolv.conf rồi “hết lỗi”: file có thể bị NetworkManager, DHCP, VPN, systemd-resolved hoặc FreeBSD resolvconf ghi lại. Sửa source of truth thay vì đấu với file sinh tự động.
  • Debian không có resolvectl: đây không tự động là lỗi. Kiểm backend DNS hiện tại; không cài systemd-resolved chỉ để có lệnh troubleshooting.
  • +trace/-T timeout: có thể outbound UDP/TCP 53 trực tiếp bị policy chặn, trong khi recursive DNS doanh nghiệp vẫn hoạt động. Trace thất bại không đồng nghĩa authoritative DNS hỏng.
  • Public domain chạy, internal domain không: nghĩ tới VPN/split DNS/search domain trước khi đổi nameserver. So sánh per-link DNS trên Linux và cấu hình resolver được cấp trên FreeBSD.
  • UDP lỗi nhưng TCP được: kiểm firewall, MTU/fragmentation và thiết bị trung gian; đừng kết luận chỉ từ một query.

06 Bảo mật & vận hành

  • Không gửi hostname nội bộ, zone AD, service discovery hoặc dữ liệu split-DNS tới resolver public để “test nhanh”; đó có thể là rò rỉ metadata và còn cho kết quả sai với kiến trúc nội bộ.
  • Không thay nameserver production trước khi lưu trạng thái cũ. Với máy remote, đổi DNS có thể làm mất package mirror, authentication, monitoring và cả tên endpoint quản trị.
  • Ưu tiên query đọc-only. Các lệnh trong bài không flush cache và không reconfigure resolver; nếu cần resolvectl flush-caches, hãy coi đó là một thao tác thay đổi trạng thái và ghi nhận trước/sau.
  • Khi thu thập bằng chứng, lưu timestamp, FQDN, server được hỏi, record type và kết quả. “DNS lúc được lúc không” chỉ điều tra được khi có cùng một bộ dữ liệu để so sánh.

07 Bài tập tự luyện

Tình huống: một host truy cập IP của web server được nhưng FQDN không mở; đồng thời VPN vừa kết nối.

  1. Dùng getent xác định NSS có resolve tên hay không.
  2. Ghi lại resolver runtime: resolvectl status trên Linux nếu service active, hoặc /etc/resolv.conf trên FreeBSD.
  3. Dùng dig/drill hỏi domain qua resolver mặc định và qua một DNS server nội bộ được quản trị viên cung cấp.
  4. Giải thích vì sao không nên dùng public resolver để thử hostname nội bộ.
  5. Chỉ khi domain public cũng có dấu hiệu delegation bất thường, dùng dig +trace hoặc drill -T và ghi rõ trace đang kiểm lớp nào.

Đầu ra: một bảng 4 dòng “NSS → resolver runtime → recursive server → authoritative chain”, mỗi dòng ghi PASS/FAIL và bằng chứng lệnh tương ứng.
