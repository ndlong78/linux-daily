Automation · Task result semantics

Ansible changed_when và failed_when: định nghĩa kết quả theo semantics thay vì chỉ exit code

Tách exit code khỏi semantics để Ansible báo changed và failed đúng với ý nghĩa vận hành.

TRỤC · AUTOMATIONĐỘ KHÓ · NÂNG CAO~13 PHÚT
Runtime tested: —Documentation verified: Ubuntu/Xubuntu 26.04 LTS · Debian 13 stable · Fedora 44 · FreeBSD 15.1-RELEASELast verified: 2026-09-14

Mục tiêu

Dùng changed_when và failed_when để biểu diễn đúng trạng thái thay đổi/thất bại của command hoặc module, tránh false positive và false failure trong automation.

Yêu cầu tiên quyết

  • Có Ansible trên control node và đã hiểu inventory, register cùng task result.
  • Ubuntu và Xubuntu dùng cùng cú pháp Ansible; Debian, Fedora và FreeBSD dùng cùng semantics của hai keyword này.
  • Lab chỉ chạy command quan sát trên localhost, không thay đổi cấu hình hệ thống.
  • Chạy bằng user thường trong thư mục lab riêng.

01 Bối cảnh thực tế

ansible.builtin.command thường xem return code khác 0 là failure, nhưng CLI thực tế có thể dùng nhiều mã để biểu diễn trạng thái hợp lệ. Ngược lại, một command có thể trả 0 nhưng stdout lại cho biết điều kiện nghiệp vụ không đạt.

Nếu chỉ dựa vào mặc định, playbook dễ báo thay đổi dù chỉ kiểm tra hoặc bỏ sót lỗi nghiệp vụ. failed_when định nghĩa “khi nào task thất bại”; changed_when định nghĩa “khi nào task thực sự thay đổi trạng thái”.

02 Kiến thức cốt lõi

  • register trước: lưu rc, stdout, stderr và các field khác để conditional đọc được.
  • failed_when: override trạng thái failure mặc định bằng biểu thức phản ánh semantics của command.
  • changed_when: override cờ changed; cờ này ảnh hưởng recap và việc notify handler.
  • List condition là AND: nhiều mục trong list failed_when/changed_when được nối ngầm bằng AND; cần OR thì viết biểu thức có or rõ ràng.
  • Không bọc {{ }}: các conditional này là raw Jinja expressions.

03 Các bước thực hiện

  1. 1. Xác nhận Ansible trên control node

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    ansible-playbook --version

    FreeBSD — CLI Ansible tương ứng, không dùng systemd

    Run as: user

    ansible-playbook --version

    Nếu command chưa có, dừng lab và cài theo package policy của hệ điều hành; bài này không thay đổi package.

  2. 2. Tạo playbook mô phỏng semantics của command

    Mọi hệ — file lab cục bộ

    Run as: user

    cat > result-semantics.yml <<'EOF'
---
- name: Result semantics lab
  hosts: localhost
  gather_facts: false
  tasks:
    - name: Simulate a command that reports an update
      ansible.builtin.command:
        argv: [/bin/sh, -c, "printf '%s\\n' UPDATED"]
      register: probe
      changed_when: "'UPDATED' in probe.stdout"
      failed_when: probe.rc != 0
EOF

    result-semantics.yml là file lab. Command chỉ in chuỗi, không sửa hệ thống; trạng thái changed ở đây dùng để quan sát cơ chế conditional.

  3. 3. Kiểm syntax trước khi chạy

    Mọi hệ

    Run as: user

    ansible-playbook -i localhost, -c local result-semantics.yml --syntax-check

    Không dùng {{ }} quanh probe.rc hoặc biểu thức changed_when/failed_when.

  4. 4. Chạy lab và đọc recap

    Mọi hệ

    Run as: user

    ansible-playbook -i localhost, -c local result-semantics.yml

    Task mô phỏng phải hiện changed vì stdout chứa UPDATED, dù command trả rc=0.

  5. 5. Kiểm một exit code hợp lệ nhưng khác 0

    Mọi hệ — thay nội dung task lab

    Run as: user

    - name: Treat rc 3 as a valid no-match state
  ansible.builtin.command:
    argv: [/bin/sh, -c, "exit 3"]
  register: probe
  failed_when: probe.rc not in [0, 3]
  changed_when: false

    Chỉ chấp nhận mã khác 0 khi tài liệu của command thật định nghĩa mã đó là trạng thái hợp lệ. Không copy [0, 3] sang production nếu command của bạn không có contract tương ứng.

04 Kiểm chứng

Chạy playbook đầu tiên và đối chiếu recap.

Mọi hệ

Run as: user

ansible-playbook -i localhost, -c local result-semantics.yml

Expected Output: task Simulate a command that reports an update có trạng thái changed; recap có failed=0. Nếu đổi chuỗi UPDATED thành UNCHANGED mà vẫn giữ conditional kiểm UPDATED, task phải về ok/changed=0.

05 Lưu ý & Khắc phục lỗi

  • Nếu conditional báo undefined, in registered result bằng ansible.builtin.debug: var=probe và kiểm đúng field trước khi sửa biểu thức.
  • Nếu cần “A hoặc B là lỗi”, dùng một biểu thức có or; list nhiều điều kiện mang semantics AND.
  • ignore_errors không thay thế failed_when: một cái cho phép tiếp tục sau failure, cái kia định nghĩa failure là gì.
  • Đừng dùng changed_when: false để che một task thật sự thay đổi hệ thống chỉ nhằm làm recap đẹp.

06 Bảo mật & vận hành

Giữ conditional gần task tạo ra result và đặt tên biến theo ý nghĩa. Với command production, ghi chú rõ exit-code contract từ tài liệu upstream. Trạng thái changed còn có thể kích hoạt handler, vì vậy false positive có thể dẫn tới reload/restart không cần thiết.

Trên Ubuntu/Xubuntu, Debian và Fedora, Ansible thường điều khiển host Linux qua SSH; FreeBSD cũng có thể là managed node nhưng service/package semantics của BSD vẫn phải tách riêng. Hai keyword trong bài thuộc Ansible task semantics, không biến lệnh Linux thành lệnh FreeBSD.

07 Bài tập tự luyện

  1. Đổi stdout thành UNCHANGED và viết changed_when để recap về ok.
  2. Mô phỏng rc=4 và xác nhận task fail khi policy chỉ chấp nhận 0 hoặc 3.
  3. Viết một biểu thức failed_when fail khi rc >= 4 hoặc stderr chứa chuỗi ERROR.
