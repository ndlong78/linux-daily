Ôn tập · File descriptor exhaustion lab

Lab file descriptor exhaustion: process limit, open-file evidence và service recovery

Giới hạn một process lab ở 64 file descriptor, chứng minh trạng thái EMFILE bằng open-file evidence rồi khôi phục sạch mà không tăng limit theo phản xạ.

TRỤC · ÔN TẬPĐỘ KHÓ · NÂNG CAO~18 PHÚT
Runtime tested: —Documentation verified: Ubuntu/Xubuntu 26.04 LTS · Debian 13 stable · Fedora 44 · FreeBSD 15.1-RELEASELast verified: 2026-09-08

Mục tiêu

Phân biệt per-process file descriptor exhaustion với system-wide exhaustion, thu thập bằng chứng trước khi thay đổi limit và xác nhận process phục hồi sau khi fault được gỡ.

Yêu cầu tiên quyết

  • Dùng VM hoặc host lab; không chạy failure injection trên production/shared host.
  • Có Python 3 và hai terminal cùng user. Lab chỉ mở tối đa khoảng 64 descriptor trong một process con và tự kết thúc sau 60 giây.
  • Ubuntu hoặc Xubuntu 26.04 LTS, Debian 13 stable và Fedora 44 dùng nhánh Linux; FreeBSD 15.1-RELEASE dùng procstat và kernel sysctl riêng.
  • Đã đọc #033, #040, #047 và #051 về process ownership, process monitoring, socket ownership và resource policy.

01 Bối cảnh thực tế

Một daemon có thể log Too many open files dù toàn hệ thống còn rất xa giới hạn. Trường hợp phổ biến là process chạm RLIMIT_NOFILE, leak descriptor theo thời gian hoặc giữ quá nhiều socket/file hợp lệ. Tăng limit ngay có thể chỉ kéo dài thời gian trước lần lỗi kế tiếp.

Lab tạo một process riêng với soft/hard limit bằng 64 rồi cố mở /dev/null cho tới khi nhận EMFILE. Ubuntu và Xubuntu dùng cùng cách quan sát Linux; Debian và Fedora cũng dùng /proc. FreeBSD tách riêng bằng procstat.

Topology lab

  • observer-shell: terminal A dùng để đọc PID, limit và open-file evidence.
  • fd-pressure-process: terminal B hoặc background process chỉ mở file descriptor trong chính process lab.

Safety boundary

  • Không sửa fs.file-max, kern.maxfiles, systemd unit hoặc login class trong lab.
  • Không chạy hàng nghìn connection/socket. Fault bị khóa ở 64 descriptor và có timeout 60 giây.
  • Không dùng PID của service production làm target. Mọi lệnh quan sát phải dùng PID đọc từ /tmp/linux-daily-070.pid.

Failure injection

Process lab tự hạ cả soft và hard RLIMIT_NOFILE xuống 64. Vì hard limit chỉ bị hạ trong process con, việc đóng process là đủ để rollback; không có thay đổi persistent.

02 Kiến thức cốt lõi

  • RLIMIT_NOFILE là giới hạn per-process; vượt giới hạn này làm thao tác mở descriptor mới thất bại với EMFILE.
  • Trên Linux, /proc/<pid>/fd liệt kê descriptor của process và /proc/<pid>/limits cho thấy soft/hard limit hiện tại.
  • Trên FreeBSD, procstat -f hiển thị file descriptor và procstat -l hiển thị resource limits của process.
  • System-wide counters là lớp khác. Một process chạm giới hạn riêng không đồng nghĩa kernel đã cạn file table.

03 Các bước thực hiện

  1. 1. Tạo process lab có giới hạn 64 descriptor

    Mọi hệ — Python 3 trên Unix

    Run as: user

    cat > /tmp/linux-daily-070-fd.py <<'PY'
import os
import resource
import time

resource.setrlimit(resource.RLIMIT_NOFILE, (64, 64))
opened = []
try:
    while True:
        opened.append(open("/dev/null", "rb"))
except OSError as exc:
    print(f"PID={os.getpid()} opened={len(opened)} errno={exc.errno} message={exc.strerror}", flush=True)
    time.sleep(60)
PY
python3 /tmp/linux-daily-070-fd.py > /tmp/linux-daily-070.log 2>&1 &
echo $! > /tmp/linux-daily-070.pid
sleep 1
cat /tmp/linux-daily-070.log

    Expected Output: một dòng có opened= gần 61 và errno=24/Too many open files. Số descriptor chính xác có thể lệch nhẹ do runtime đã mở stdin/stdout/stderr.

  2. 2. Đọc per-process evidence trên Linux

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: user

    PID=$(cat /tmp/linux-daily-070.pid)
ls -1 "/proc/${PID}/fd" | wc -l
grep 'Max open files' "/proc/${PID}/limits"
cat /proc/sys/fs/file-nr

    Expected Output: số descriptor tiến sát 64; dòng Max open files có soft/hard limit 64. file-nr cho system-wide allocation để tránh nhầm per-process exhaustion với cạn file table toàn host.

  3. 3. Đọc evidence tương đương trên FreeBSD

    FreeBSD — KHÁC Linux

    Run as: user

    PID=$(cat /tmp/linux-daily-070.pid)
procstat -f "${PID}"
procstat -l "${PID}"
sysctl kern.openfiles kern.maxfiles

    Expected Output: procstat -f liệt kê nhiều descriptor thuộc process lab; procstat -l cho thấy resource limit của process; kern.openfiles còn thấp hơn đáng kể so với kern.maxfiles trong một host lab bình thường.

  4. 4. Phân loại lỗi trước khi tuning

    Nếu process đã gần 64 nhưng system-wide counter còn xa ceiling, kết luận lab đang gặp per-process exhaustion. Trong incident thật, bước tiếp theo là tìm descriptor tăng theo thời gian, loại descriptor và ownership; không tăng limit trước khi biết growth có hợp lệ hay là leak.

  5. 5. Gỡ fault và kiểm process recovery boundary

    Mọi hệ

    Run as: user

    PID=$(cat /tmp/linux-daily-070.pid)
kill "${PID}" 2>/dev/null || true
sleep 1
ps -p "${PID}"

    Expected Output: ps không còn hiển thị process lab. Với service thật, recovery phải bổ sung service-state check và functional probe riêng; restart chỉ là boundary phục hồi, không phải root-cause fix.

04 Kiểm chứng

  • Negative: process lab thật sự nhận EMFILE ở limit 64.
  • Observability: open-file count tiến sát process limit, trong khi system-wide counter chưa cạn.
  • Recovery: process fault đã dừng và không còn giữ descriptor.

Expected Output / Kết quả mong đợi

Evidence phải hỗ trợ kết luận “per-process limit bị chạm” thay vì “toàn hệ thống hết file descriptor”. Không có kernel tunable hoặc service configuration nào bị thay đổi.

Rollback lab

Rollback là dừng process lab. setrlimit() chỉ tác động process con; khi process kết thúc, limit 64 biến mất cùng process và không cần khôi phục kernel setting.

Cleanup lab

Mọi hệ

Run as: user

rm -f /tmp/linux-daily-070-fd.py /tmp/linux-daily-070.log /tmp/linux-daily-070.pid

Expected Output: ba file tạm không còn tồn tại; không còn process linux-daily-070-fd.py chạy nền.

05 Lưu ý & Khắc phục lỗi

  • Nếu process đã tự kết thúc trước khi quan sát, chạy lại bước 1; timeout 60 giây là safety boundary có chủ ý.
  • Nếu /proc/<pid>/fd báo permission denied trên Linux, kiểm ownership của process và policy bảo vệ /proc; không dùng root chỉ để né policy khi chưa cần.
  • Nếu procstat không đọc được process FreeBSD, kiểm process còn sống và chạy cùng owner.
  • Nếu system-wide counter cũng sát ceiling trong incident thật, dừng ở bước phân loại và mở investigation riêng; không dùng lab này để tăng kernel ceiling.

06 Bảo mật & vận hành

  • File descriptor có thể trỏ tới socket, pipe, credential-backed file hoặc path nhạy cảm. Khi lưu evidence, tránh công khai pathname/socket metadata không cần thiết.
  • Giữ baseline trước incident: process limit, open descriptor count và growth rate. Một snapshot đơn lẻ cho biết trạng thái; trend mới giúp phát hiện leak.
  • Chỉ tăng limit sau khi đã chứng minh workload hợp lệ cần headroom và đã kiểm memory/socket/kernel capacity liên quan.

07 Bài tập tự luyện

  1. Đổi limit process lab từ 64 xuống 32 và dự đoán số file mở thành công trước khi chạy.
  2. Phân loại descriptor trong output procstat -f hoặc /proc/<pid>/fd thành file, pipe và socket trên một process lab khác.
  3. Viết checklist incident gồm ba câu hỏi: process limit là bao nhiêu, hiện đang dùng bao nhiêu, system-wide headroom còn bao nhiêu.
