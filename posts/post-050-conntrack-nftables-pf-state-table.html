Networking · firewall state

State table: conntrack/nftables trên Linux và pf state trên FreeBSD

Đọc state trước khi sửa rule: phân biệt flow đang được theo dõi, timeout và dấu hiệu asymmetric routing trên Linux lẫn FreeBSD.

TRỤC · NETWORKINGĐỘ KHÓ · NÂNG CAO~12 PHÚT

Tested on: Ubuntu/Xubuntu 24.04 LTS · Debian 13 stable · Fedora 42 · FreeBSD 14.4-RELEASE

Last verified: 2026-08-19 · đối chiếu Linux kernel conntrack, nftables upstream và tài liệu PF của FreeBSD.

Mục tiêu

Dùng state table như bằng chứng vận hành: xác định flow có được firewall theo dõi hay không, đọc trạng thái TCP/UDP và nhận diện khi đường đi hai chiều không cùng qua một firewall.

Yêu cầu tiên quyết

  • Đã nắm firewall cơ bản ở #007/#020, policy routing ở #029 và packet capture ở #036.
  • Có quyền sudo/root trên máy lab. Không xoá state trên production trong bài này.
  • Linux dùng netfilter/nftables; FreeBSD dùng PF. Hai state engine có khái niệm gần nhau nhưng không đồng nhất cú pháp.

01 Bối cảnh thực tế

Một rule cho TCP/443 có vẻ đúng nhưng client vẫn treo, hoặc bạn vừa sửa firewall mà một kết nối cũ vẫn chạy. Nếu chỉ nhìn ruleset, bạn đang thiếu nửa bức tranh: state table. Trên Linux, connection tracking của netfilter lưu thông tin flow và nftables có thể match các metadata như ct state established,related. Trên FreeBSD PF, state được tạo từ các rule stateful và xem bằng pfctl -ss.

State table đặc biệt hữu ích khi debug asymmetric routing. Nếu SYN đi qua firewall A nhưng SYN-ACK quay qua firewall B, mỗi thiết bị chỉ thấy một nửa hội thoại. Kết quả thường là state không tiến triển như mong đợi, dù route riêng lẻ và rule riêng lẻ nhìn có vẻ hợp lý.

02 Kiến thức cốt lõi

  • Flow identity: thường dựa trên protocol, địa chỉ và port hai đầu; NAT có thể khiến state giữ thêm tuple trước/sau dịch.
  • Linux: conntrack là subsystem của netfilter; nftables đọc metadata conntrack nhưng không phải bản thân state table.
  • FreeBSD PF: pfctl -ss hiển thị states; timeout và state-policy nằm trong semantics của PF.
  • ESTABLISHED không đồng nghĩa ứng dụng khỏe: nó chỉ là bằng chứng ở lớp state/transport. Vẫn cần log ứng dụng và packet capture khi cần.
  • Không xoá state để “thử xem”: flush state có thể cắt kết nối hợp lệ và che mất bằng chứng.

Khác biệt theo hệ điều hành

Ubuntu/Xubuntu và Debian: package conntrack cung cấp CLI xem state; nft dùng để xem ruleset. Cài package chỉ khi lab chưa có.

Fedora: package CLI thường là conntrack-tools; nftables vẫn dùng netfilter/conntrack của kernel.

FreeBSD

FreeBSD tách riêng: PF dùng pfctl; không áp nft, conntrack hoặc systemctl cho PF.

03 Các bước thực hiện

  1. Chụp baseline ruleset và state count trên Linux

    Ubuntu / Xubuntu / Debian

    Run as: sudo

    sudo nft list ruleset
sudo sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max

    Không chỉnh rule ở bước này. Mục tiêu là biết ruleset nào đang chạy và state table đang dùng bao nhiêu entry.

    Fedora

    Run as: sudo

    sudo nft list ruleset
sudo sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max

  2. Liệt kê flow TCP và lọc dịch vụ 443 trên Linux

    Run as: sudo

    sudo conntrack -L -p tcp
sudo conntrack -L -p tcp --dport 443

    Nếu lệnh chưa có: Ubuntu/Xubuntu/Debian cài package conntrack; Fedora cài conntrack-tools. Trên production, ưu tiên cửa sổ quan sát ngắn vì bảng lớn có thể tạo output nhiều.

  3. Đối chiếu rule nào dùng connection state

    Run as: sudo

    sudo nft -a list ruleset | grep -E 'ct state|ct status|ct mark'

    Không kết luận rằng mọi rule stateful phải chứa đúng chuỗi này: ruleset có thể được tạo bởi firewalld hoặc cấu trúc chain khác. Hãy dùng output này để tìm điểm bắt đầu rồi đọc toàn chain.

  4. Đọc PF states trên FreeBSD

    FreeBSD

    Run as: root

    pfctl -si
pfctl -ss
pfctl -vvs state

    pfctl -si cho thống kê tổng quát; -ss liệt kê state; -vvs state tăng chi tiết để đối chiếu interface, counters và timeout.

  5. Kiểm tra asymmetric path bằng packet capture

    Trên Linux dùng tcpdump tại interface ingress/egress; trên FreeBSD cũng có tcpdump. Quan sát cùng một kết nối và xác nhận SYN, SYN-ACK, ACK có đi qua cùng stateful firewall hay không.

    Run as: sudo

    sudo tcpdump -ni any 'tcp port 443 and (tcp[tcpflags] & (tcp-syn|tcp-ack) != 0)'

04 Kiểm chứng

Expected Output / Kết quả mong đợi:

  • Linux: nf_conntrack_count nhỏ hơn nf_conntrack_max; conntrack -L có flow phù hợp với traffic đang tạo.
  • Nftables: ruleset cho thấy nơi dùng ct state hoặc policy stateful tương ứng.
  • FreeBSD: pfctl -ss có state cho traffic đang kiểm tra và counters thay đổi khi có packet mới.
  • Packet capture: hai chiều của handshake xuất hiện trên firewall dự kiến. Nếu chỉ thấy một chiều, quay lại routing/policy routing trước khi sửa firewall rule.

Run as: sudo

sudo conntrack -S
sudo nft list ruleset | grep -E 'ct state|established|related'

FreeBSD verification

Run as: root

pfctl -si
pfctl -ss | head -n 20

05 Lưu ý & Khắc phục lỗi

  • conntrack: command not found: cài CLI đúng distro; kernel conntrack có thể vẫn đang hoạt động dù CLI chưa cài.
  • nf_conntrack_count không tồn tại: kiểm tra module/subsystem conntrack có được sử dụng trên host hay không; đừng tự load module trên production chỉ để có metric.
  • State table gần đầy: không tăng nf_conntrack_max theo phản xạ. Xác định nguồn flow, timeout, scan/abuse và RAM budget trước.
  • Rule đã sửa nhưng kết nối cũ vẫn khác kỳ vọng: state cũ có thể còn hiệu lực. Thu bằng chứng trước; tránh flush toàn bảng.
  • PF không có state: kiểm tra PF có enable, rule có tạo state và traffic thực sự đi qua interface/rule dự kiến.

06 Bảo mật & vận hành

State table chứa địa chỉ, port và topology vận hành nên output có thể nhạy cảm. Khi đưa vào ticket/chat, che địa chỉ nội bộ hoặc public IP nếu chính sách yêu cầu. Với máy biên có state table lớn, tránh dump liên tục vì vừa tốn CPU/I/O vừa tạo log khó kiểm soát.

Không dùng conntrack -F hoặc pfctl -F states như bước debug mặc định. Hai lệnh đó thay đổi trạng thái hệ thống và có thể cắt kết nối đang hoạt động; bài này cố ý chỉ quan sát.

07 Bài tập tự luyện

  1. Tạo một kết nối HTTPS hợp lệ, tìm đúng flow trong state table và ghi lại tuple hai chiều.
  2. So sánh output trước, trong và sau khi kết nối đóng; quan sát state còn tồn tại bao lâu.
  3. Vẽ đường đi của một flow qua hai router/firewall và chỉ ra vị trí asymmetric routing có thể phá stateful inspection.
  4. Trên FreeBSD, đối chiếu một state từ pfctl -ss với rule tương ứng trong pfctl -sr.
