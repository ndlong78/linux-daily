Lab certificate renewal race: file ownership, service reload và rollback evidence

Chứng minh certificate trên disk, quyền đọc của service và certificate đang được phục vụ là ba trạng thái khác nhau trước khi reload hoặc rollback.

TRỤC · ÔN TẬPĐỘ KHÓ · NÂNG CAO~14 PHÚT
Runtime tested: —Documentation verified: Ubuntu/Xubuntu 26.04 LTS · Debian 13 stable · Fedora 44 · FreeBSD 15.1-RELEASELast verified: 2026-09-15

Mục tiêu

Khoanh vùng renewal race bằng fingerprint, ownership và reload evidence trước khi rollback certificate.

Yêu cầu tiên quyết

  • Có OpenSSL và quyền đọc certificate cần kiểm tra.
  • Biết chính xác đường dẫn certificate, tên service và endpoint TLS của lab.
  • Ubuntu và Xubuntu dùng systemd; Debian và Fedora cũng dùng systemd, còn FreeBSD dùng rc.d/service.

01 Bối cảnh thực tế

Certificate mới có thể đã nằm trên disk nhưng daemon vẫn giữ certificate cũ trong memory. Một race khác xảy ra khi file mới có owner, group hoặc mode khiến daemon không đọc được. Đừng quy mọi mismatch sau renewal thành lỗi TLS chain.

02 Kiến thức cốt lõi

  • openssl x509 -fingerprint nhận diện certificate; -dates đọc thời hạn.
  • Fingerprint local và remote khác nhau cho thấy deployment state chưa hội tụ.
  • Reload chỉ thực hiện sau khi kiểm cấu hình và quyền file; restart không phải bước chẩn đoán đầu tiên.
  • Rollback phải khôi phục cả file và reload state, rồi kiểm lại endpoint.

03 Các bước thực hiện

  1. 1. Ghi evidence trước thay đổi

    Mọi hệ

    Run as: sudo

    sudo stat <certificate-path>
sudo openssl x509 -in <certificate-path> -noout -fingerprint -sha256 -dates

    <certificate-path> là file certificate thật của service, xác định từ cấu hình trước khi chạy.

  2. 2. So fingerprint endpoint

    Mọi hệ

    Run as: user

    openssl s_client -connect <host>:<port> -servername <host> </dev/null 2>/dev/null | openssl x509 -noout -fingerprint -sha256 -dates

    <host> và <port> là endpoint lab đã xác minh.

  3. 3. Kiểm service trước reload

    Ubuntu/Xubuntu · Debian · Fedora

    Run as: sudo

    sudo systemctl status <service-name> --no-pager
sudo systemctl reload <service-name>

    FreeBSD — rc.d

    Run as: root

    service <service-name> status
service <service-name> reload

    <service-name> phải lấy từ service đang phục vụ endpoint; chỉ reload sau khi config test riêng của daemon đã pass.

  4. 4. Lặp lại remote fingerprint

    Mọi hệ

    Run as: user

    openssl s_client -connect <host>:<port> -servername <host> </dev/null 2>/dev/null | openssl x509 -noout -fingerprint -sha256

04 Kiểm chứng

Expected Output: SHA-256 fingerprint của certificate local khớp fingerprint endpoint sau reload; notAfter là thời hạn mong đợi; service vẫn ở trạng thái running.

Gỡ / Hoàn tác

Nếu reload lỗi hoặc endpoint không phục vụ certificate mong đợi, khôi phục bản backup certificate/key và metadata owner/group/mode đã ghi trước thay đổi, chạy config test của daemon, reload lại bằng đúng cơ chế Linux hoặc FreeBSD ở trên, rồi lặp lại fingerprint remote. Không xóa certificate cũ trước khi rollback được kiểm chứng.

05 Lưu ý & Khắc phục lỗi

  • Nếu local fingerprint đúng nhưng remote vẫn cũ, kiểm load balancer/proxy và process thực sự giữ socket trước khi reload lặp lại.
  • Nếu reload báo permission denied, so owner/group/mode với backup; không chữa bằng chmod 777.
  • Nếu certificate và private key không thuộc cùng deployment set, dừng thay đổi và quay lại backup đã xác minh.

06 Bảo mật & vận hành

Không in private key vào terminal hoặc log. Giữ quyền đọc key tối thiểu cho daemon. Trên Ubuntu, Xubuntu, Debian và Fedora, systemd quản lý service; FreeBSD dùng rc.d và service(8), không áp systemctl cho FreeBSD.

07 Bài tập tự luyện

  1. Lập bảng ba fingerprint: expected, local và remote.
  2. Mô tả cách phân biệt file permission regression với service chưa reload mà không restart mù.
  3. Viết checklist rollback gồm file, metadata, config test, reload và remote verification.
