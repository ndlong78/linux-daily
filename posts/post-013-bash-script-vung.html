Script chạy tốt trên máy bạn, vỡ trên máy chủ — vì sao?

Bạn viết một script, chạy ngon trên laptop Fedora, đẩy lên server Debian thì lỗi tùm lum. Thủ phạm thường không phải logic mà là môi trường: /bin/sh trỏ vào shell khác nhau trên mỗi hệ, và script thiếu xử lý lỗi nên hỏng trong im lặng. Bài này chỉ cách chọn shebang đúng, bật chế độ nghiêm, và viết script vững để "chạy được ở đây" đồng nghĩa "chạy được mọi nơi".

TRỤC · AUTOMATION ĐỘ KHÓ · TRUNG CẤP ~10 PHÚT

01 Bối cảnh thực tế

Một script có thể chạy trên máy phát triển nhưng hỏng trên máy chủ vì /bin/sh không nhất thiết là cùng một shell. Ubuntu/Debian thường dùng dash cho /bin/sh; Fedora có thể chạy Bash ở chế độ tương thích sh; FreeBSD có /bin/sh của hệ base. Vì vậy, nếu script cần mảng, [[ ... ]] hay pipefail, hãy nói rõ rằng đó là Bash.

02 Kiến thức cốt lõi

  • #!/bin/sh: dành cho script viết theo cú pháp shell khả chuyển; không dùng bashism.
  • #!/usr/bin/env bash: hữu ích khi Bash nằm ở vị trí khác nhau, nhưng env tìm bash qua PATH. Với cron, systemd, sudo hay môi trường bị thu gọn, phải biết PATH thực tế là gì.
  • set -euo pipefail: là một bộ guardrail tốt cho Bash, không phải cơ chế xử lý lỗi hoàn chỉnh. Đặc biệt -e có ngoại lệ theo ngữ cảnh điều kiện, danh sách &&/||, pipeline và một số cấu trúc khác.
  • Không đổi global IFS theo thói quen: ưu tiên quote biến, dùng array khi cần, hoặc đặt IFS= cục bộ cho đúng thao tác đọc/tách trường.

03 Viết một script Bash vững

Khung chung — Bash + cleanup 
#!/usr/bin/env bash
set -euo pipefail

tmp="$(mktemp)"
cleanup() { rm -f -- "$tmp"; }
trap cleanup EXIT

src="${1:?cần đối số: đường dẫn nguồn}"
cp -- "$src" "$tmp"
printf 'Đã xử lý: %s\n' "$src"

Không đặt IFS=$'\n\t' toàn cục nếu không có nhu cầu cụ thể. Quote biến mới là nền tảng. Khi cần đọc dữ liệu theo delimiter, đặt IFS cục bộ, ví dụ while IFS= read -r line.

Linux — kiểm interpreter 
command -v bash
bash --version
chmod +x script.sh
./script.sh /etc/hostname
FreeBSD — Bash ngoài base 
pkg install -y bash
command -v bash
# thường: /usr/local/bin/bash
./script.sh /etc/hostname

04 Kiểm chứng

shellcheck script.sh
bash -n script.sh
command -v bash

env -i PATH="/usr/bin:/bin" bash -c 'printf "%s\n" "$PATH"'

Lệnh cuối minh hoạ vì sao môi trường chạy quan trọng: khi PATH bị thay đổi, env cũng thay đổi cách tìm interpreter. Với job tự động, ghi rõ hoặc kiểm tra PATH thay vì giả định.

05 Cạm bẫy thường gặp

  • Hiểu sai set -e: không phải mọi non-zero đều làm script thoát. Với bước quan trọng, kiểm trạng thái rõ ràng hoặc dùng cấu trúc if ! command; then ...; fi.
  • env bash dưới sudo/cron: có thể gặp PATH khác phiên shell tương tác. Nếu môi trường được kiểm soát chặt và đường dẫn Bash cố định, shebang tuyệt đối cũng là lựa chọn hợp lệ.
  • Dùng which để kiểm availability: trong script shell, ưu tiên command -v bash.
  • Lệnh xoá với biến rỗng: rm -rf "$dir"/ có thể biến thành target gốc nếu biến rỗng. GNU rm mặc định có --preserve-root, nhưng script không được dựa vào guardrail đó; hãy validate biến trước lệnh destructive.

06 Lưu ý bảo mật & vận hành

  • Trước thao tác destructive, kiểm biến: : "${dir:?dir phải được đặt}" và giới hạn đường dẫn hợp lệ.
  • Quote mọi expansion cần quote và dùng -- khi utility hỗ trợ để chặn operand bắt đầu bằng dấu gạch ngang.
  • Đưa shellcheck và test dưới đúng interpreter vào CI.
  • Job chạy bằng cron/systemd phải có môi trường dự đoán được, đặc biệt là PATH, working directory và quyền user.

07 Bài tập tự luyện

Tạo một script dùng Bash array. Chạy thử với #!/bin/sh và với #!/usr/bin/env bash. Sau đó chạy trong môi trường có PATH tối giản để quan sát cách env tìm interpreter. Cuối cùng, thay một lệnh bằng lệnh trả mã lỗi trong if và trong pipeline để xem hành vi thực tế của set -e/pipefail.
